Да. Тут «адаптер» — не какая-то отдельная сложная технология. Это просто **тонкий слой кода, который переводит API твоего ядра в формат, понятный конкретному агенту или MCP**.

Самая важная идея такая:

```text
                 ┌─────────────────────┐
                 │     1C Tool Core    │
                 │                     │
                 │ run_1c()            │
                 │ update_db()         │
                 │ run_tests()         │
                 │ get_log()           │
                 │ dump_config()       │
                 └──────────┬──────────┘
                            │
              ┌─────────────┴─────────────┐
              │                           │
        Direct adapter                MCP adapter
              │                           │
            Codex                  Cursor / Claude
```

То есть **реальная работа с `1cv8.exe` написана один раз**.

Адаптеры только принимают запрос в разных форматах и вызывают одно и то же ядро.

## Самый простой пример

Допустим, у тебя есть Python-модуль:

```python
# onec_core.py

import subprocess


def update_db(infobase: str):
    result = subprocess.run(
        [
            r"C:\Program Files\1cv8\8.3.27.1508\bin\1cv8.exe",
            "DESIGNER",
            "/F", infobase,
            "/UpdateDBCfg"
        ],
        capture_output=True,
        text=True
    )

    return {
        "exit_code": result.returncode,
        "stdout": result.stdout,
        "stderr": result.stderr,
    }


def run_tests(infobase: str):
    # условно запуск Vanessa / YaXUnit
    ...
```

Это и есть условный:

```text
1C Tool Core
```

Он вообще не знает, кто его вызывает:

* Codex;
* Claude;
* MCP;
* CLI;
* твой Intelligence-researcher;
* обычный человек из PowerShell.

Ему всё равно.

## Вариант №1. Direct adapter

Допустим, Codex SDK позволяет зарегистрировать функции/tools.

Условно API выглядит так:

```python
agent.register_tool(
    name="update_1c_database",
    description="Обновить конфигурацию базы данных 1С",
    schema={
        "infobase": "string"
    },
    handler=...
)
```

Ты пишешь адаптер:

```python
# codex_adapter.py

from onec_core import update_db


def update_1c_database(infobase: str):
    return update_db(infobase)
```

И регистрируешь:

```python
agent.register_tool(
    name="update_1c_database",
    description="Обновляет конфигурацию базы 1С",
    handler=update_1c_database
)
```

Получается:

```text
Codex

решил вызвать:

update_1c_database({
    "infobase": "C:\\Bases\\Test"
})

        ↓

Codex adapter

        ↓

onec_core.update_db()

        ↓

1cv8.exe DESIGNER /F C:\Bases\Test /UpdateDBCfg
```

Codex видит только:

```text
tool: update_1c_database
```

Он даже может не знать, что внутри запускается `1cv8.exe`.

# Вариант №2. MCP adapter

Теперь ты хочешь то же самое показать через MCP.

Твой MCP server примерно такой:

```python
# mcp_adapter.py

from mcp.server.fastmcp import FastMCP
from onec_core import update_db, run_tests

mcp = FastMCP("1C Tools")


@mcp.tool()
def update_1c_database(infobase: str):
    """Обновить конфигурацию базы данных 1С."""
    return update_db(infobase)


@mcp.tool()
def run_1c_tests(infobase: str):
    """Запустить тесты 1С."""
    return run_tests(infobase)


mcp.run()
```

Обрати внимание.

Здесь **MCP-код практически ничего не делает**.

Он просто говорит:

```python
@mcp.tool()
def update_1c_database(...):
    return update_db(...)
```

То есть:

```text
MCP request

        ↓

MCP adapter

        ↓

update_db()

        ↓

1C Tool Core

        ↓

1cv8.exe
```

Вот именно этот маленький кусочек я называю **адаптером**.

---

# А зачем вообще это разделять

Можно ведь написать сразу:

```python
@mcp.tool()
def update_1c_database(...):
    subprocess.run(["1cv8.exe", ...])
```

Конечно.

Но тогда твоя архитектура становится:

```text
MCP server
    │
    ├── запуск 1С
    ├── работа с логами
    ├── Vanessa
    ├── обновление БД
    ├── поиск платформы
    ├── таймауты
    ├── блокировки
    └── обработка ошибок
```

Через некоторое время у тебя будет MCP-сервер на 20 000 строк.

А потом захочешь дать эти же функции Codex напрямую.

И выяснится:

> А вся логика-то внутри MCP-сервера.

Придётся либо вызывать MCP из Codex, либо вытаскивать всё обратно.

Если сразу сделать:

```text
onec-core
    │
    ├── platform.py
    ├── database.py
    ├── runner.py
    ├── tests.py
    ├── logs.py
    └── metadata.py

adapters/
    ├── mcp.py
    ├── codex.py
    ├── claude.py
    └── cli.py
```

то проблемы нет.

# И для твоего случая я бы пошёл ещё дальше

У тебя ведь потенциально не просто:

```text
run 1cv8.exe
```

а гораздо более серьёзная система.

Например ядро могло бы предоставить:

```text
platform.detect()

designer.load_cfg()
designer.dump_cfg()
designer.load_files()

logs.read_eventlog()

metadata.get_objects()

syntax.check()

session.wait_until_ready()
session.kill()
```

А сверху это может выглядеть совсем по-разному.

### Для человека

```bash
onec tests run --base test --suite smoke
```

### Для Python

```python
result = onec.tests.run(
    base="test",
    suite="smoke"
)
```

### Для Codex

```text
Tool:

run_1c_tests
{
    "base": "test",
    "suite": "smoke"
}
```

### Для MCP

```text
tools/call

name = "run_1c_tests"

arguments = {
    "base": "test",
    "suite": "smoke"
}
```

Все четыре вызывают одну функцию:

```python
core.tests.run(...)
```

Это и есть смысл адаптеров.

# Есть ещё один важный слой

Я бы даже сделал не:

```text
MCP → subprocess → 1cv8.exe
```

а:

```text
                           ┌─ MCP adapter
                           │
                           ├─ Codex adapter
                           │
                           ├─ CLI adapter
                           │
                           ▼
                    ┌─────────────┐
                    │ 1C Tool API │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │ 1C Runtime  │
                    │             │
                    │ processes   │
                    │ locks       │
                    │ sessions    │
                    │ temp dirs   │
                    │ logs        │
                    │ timeouts    │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │   1cv8.exe  │
                    └─────────────┘
```

Потому что довольно скоро начинаются вещи вроде:

```text
А база сейчас занята?

А Designer уже запущен?

А Enterprise не висит?

Какой PID относится к этому тесту?

Где временный каталог?

Какая версия платформы?

Процесс умер или ещё выполняется?

Где лог?

А агент запустил два update одновременно?

А тест завис на модальном окне?
```

Эта логика **не должна находиться ни в MCP, ни в Codex adapter**.

Она должна находиться внутри ядра.

# Очень конкретный пример для твоей схемы Agent → Vanessa → 1С

Например агент делает изменение в BSL.

После этого:

```text
Codex
 │
 │ run_tests(base="dev")
 ▼
Codex adapter
 │
 ▼
TestService.run()
 │
 ├─ убедиться, что база существует
 ├─ дождаться отсутствия блокировки
 ├─ обновить конфигурацию
 ├─ запустить 1С
 ├─ запустить Vanessa
 ├─ дождаться окончания
 ├─ забрать XML/JSON отчёт
 └─ разобрать результат
 │
 ▼
{
    "status": "failed",
    "passed": 37,
    "failed": 2,
    "failures": [
       {
          "scenario": "...",
          "message": "...",
          "stack": "..."
       }
    ]
}
```

И Codex получает **не мешанину stdout от `1cv8.exe`**, а нормальный результат:

```json
{
  "passed": 37,
  "failed": 2
}
```

Тот же самый:

```python
TestService.run()
```

может вызываться через MCP:

```text
Claude
  ↓
MCP
  ↓
TestService.run()
```

Вот здесь разделение начинает приносить огромную пользу.

## Адаптер можно представить как переходник USB

Есть устройство:

```text
1C Tool Core
```

Есть разные разъёмы:

```text
Codex tools
MCP
CLI
HTTP
Python
```

Ты не производишь пять разных устройств.

Ты делаешь:

```text
       ┌─ USB-C переходник
устройство ─ HDMI переходник
       ├─ Ethernet переходник
       └─ ...
```

Само устройство остаётся тем же.

### Поэтому для `1C-Migration-Lab` я бы физически раскладывал проект примерно так

```text
onec-agent-tools/

  core/
    platform.py
    process.py
    infobase.py
    configuration.py
    enterprise.py
    tests.py
    logs.py
    metadata.py

  adapters/
    cli/
    mcp/
    codex/

  tests/

  pyproject.toml
```

И правило:

> **В `adapters/mcp` запрещена бизнес-логика работы с 1С.
> В `adapters/codex` запрещена бизнес-логика работы с 1С.**

Там только преобразование:

```text
входной формат
      ↓
вызов core
      ↓
выходной формат
```

Это позволит тебе потом спокойно решить: **CodePilot пусть работает через MCP, Codex Worker — напрямую, а Intelligence-researcher — через Python API**, при этом все трое фактически используют один и тот же механизм запуска и проверки 1С.
