Да. Тут на самом деле обсуждались **две разные, но дополняющие друг друга проблемы**:

1. как дать агенту **«мозг» для понимания огромной конфигурации 1С**;
2. как дать ему **«глаза и руки»**, чтобы он после изменения кода реально запустил 1С и доказал, что всё работает.

И вот если соединить эти две части, получается уже почти полноценный автономный разработчик 1С.

### 1. Поиск и понимание большой конфигурации

Обычный coding-agent умеет `grep`, читать файлы, искать имена процедур. Для небольшого проекта этого хватает. Для ERP/УТ/Розницы — быстро начинается беда: десятки тысяч файлов, XML метаданных, формы, СКД, роли, обработчики событий, подписки и огромные общие модули.

В старом чате Андрей описывал уже работающий прототип: **информация собирается через RLM, затем результат валидируется BSL Language Server; на вход агенту дают ТЗ, git-ветку, расширение и конфигурацию**. 

То есть модель не должна получать всю конфигурацию в prompt. Она получает **инструменты исследования**.

Схематично:

```text
           вопрос агента
                │
                ▼
       инструмент навигации
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
      BSL      XML    metadata
       │        │        │
       └───── связи ─────┘
                │
                ▼
     маленький релевантный
       кусок информации
                │
                ▼
               LLM
```

#### `rlm-tools-bsl`

Вот этот проект особенно интересен для твоей задачи.

Идея там примерно такая: **не тащить найденные файлы в контекст модели, а позволить агенту выполнять вычисления рядом с кодовой базой и вернуть только результат**.

Допустим, агент хочет узнать:

> Где формируется движение регистра X при проведении Реализации?

Плохой вариант:

```text
grep -> 300 совпадений
      ↓
300 совпадений в context
      ↓
прочитать 10 модулей
      ↓
context раздувается
```

RLM-подход:

```text
агент
  ↓
найди объект
  ↓
найди методы проведения
  ↓
найди вызовы регистра X
  ↓
построй callers/callees вокруг этих методов
  ↓
print только 15 нужных строк
```

Текущий `rlm-tools-bsl` уже именно так и позиционируется: MCP для токен-эффективного анализа крупных BSL-кодовых баз, с десятками специализированных helper'ов, опциональным SQLite-индексом, поиском ссылок на метаданные и построением локального call graph. У него даже есть `llm_query`, позволяющий отдать промежуточную фильтрацию маленькой модели **внутри сервера**, не загрязняя контекст главного агента. ([GitHub][1])

И интересна история автора из того чата. Он писал `rlm-tools-bsl` практически агентами: локальные правила, планы, мини-спеки, память, техдокументация, unit-тесты, натурные тесты и несколько больших каталогов исходников 1С для проверки поиска. Но когда кодовая база выросла, выяснилось, что **даже десятки AI-review не заменяют человека, который понимает архитектуру**: начали появляться противоречия контрактов и сильная связанность. 

Для нашего `Intelligence-researcher` это, кстати, очень ценный отрицательный опыт.

### 2. `code-index-mcp` — немного другая философия

И здесь я поправлю свой предыдущий ответ: **`code-index-mcp` буквально в том Telegram-чате не обсуждался**. Он появился в нашем последующем исследовании `1C-Migration-Lab`, и я смешал эти два источника.

Но он решает ту же фундаментальную проблему другим способом.

`code-index-mcp` заранее строит **структурный индекс**:

```text
BSL/XML
   ↓
 parser
   ↓
structural index
   │
   ├── procedures/functions
   ├── callers
   ├── callees
   ├── metadata
   ├── form handlers
   └── event subscriptions
```

После этого агент спрашивает:

```text
get_callers("РассчитатьСумму")
get_callees(...)
get_function(...)
```

и получает точный структурный ответ, а не результаты grep. Сейчас Code Index описывает поиск функций, callers/callees, получение одного тела функции и карту модуля без чтения всего файла; для 1С отдельно индексируются BSL и XML. ([Инфостарт][2])

То есть грубо:

| инструмент       | философия                                                                         |
| ---------------- | --------------------------------------------------------------------------------- |
| `grep/ripgrep`   | ищи текст                                                                         |
| `code-index-mcp` | заранее построй структурную карту                                                 |
| `rlm-tools-bsl`  | дай агенту инструменты исследовать репозиторий и программно фильтровать результат |
| Unica            | дай агенту уже целую рабочую среду для разработки 1С                              |

И **code-index + RLM вовсе не обязательно конкуренты**. Я бы даже рассматривал:

```text
быстрые детерминированные вопросы
        ↓
   code-index-mcp

сложное исследование,
нестандартный поиск
        ↓
   rlm-tools-bsl
```

### 3. А Unica уже заметно шире обоих

В чате Игорь Апресов показывал Unica и писал, что в новой архитектуре получил более чем **100-кратное улучшение оптимизации контекста** — это заявление автора из чата, не независимый benchmark. 

Позже в обсуждении отдельно отмечалось, что Unica содержит знания/инструментарий для **СКД, макетов, форм, метаданных и прав**. 

А сейчас проект развился ещё дальше. Текущая Unica — уже плагин для Codex и Claude Code с единым MCP `unica`; он умеет создавать и проверять метаданные, формы, роли, СКД, внешние обработки/отчёты, искать BSL и **запускать 1С**. ([GitHub][3])

То есть Unica — уже скорее:

```text
           CODING AGENT
                │
              Unica
      ┌─────────┼──────────┐
      ▼         ▼          ▼
    поиск     изменение    знания
     BSL       XML/BSL       1С
      │         │
      ├── формы
      ├── СКД
      ├── роли
      └── метаданные
                │
                ▼
             запуск 1С
```

Это значительно ближе к **готовой agent development environment**, чем просто индексатор.

## 4. BSL Language Server — это не поиск, а «компилятор здравого смысла»

Это ещё одна важная часть.

В том чате участники очень высоко оценивали BSL Language Server именно потому, что у его диагностик есть не просто правило вида:

> «так нельзя».

А структура вроде:

```text
diagnostic
why bad
exceptions
bad example
good example
algorithm
quick fix
source
```

На тот момент участник чата насчитал 186 диагностик и отдельно подчеркивал наличие как плохих, так и корректных test fixtures. 

Для LLM это золото.

Например модель сгенерировала:

```1c
НачатьТранзакцию();

...

ЗафиксироватьТранзакцию();
```

Но забыла правильный `Попытка/Исключение` и откат.

Агент сам может быть уверен:

> «готово».

BSL LS говорит:

```text
WrongUseOfRollbackTransactionMethod
PairingBrokenTransaction
CommitTransactionOutsideTryCatch
...
```

И агент получает **объективный feedback**, а не мнение второй LLM.

Сейчас BSL Language Server умеет работать и в MCP mode; помимо диагностики у него есть LSP-возможности вроде перехода к определению и type-aware completion. ([GitHub][4])

Поэтому хороший цикл получается такой:

```text
       LLM пишет BSL
             │
             ▼
     BSL Language Server
             │
       ┌─────┴─────┐
       │           │
    ошибок нет    ошибки
       │           │
       │           ▼
       │       LLM исправляет
       │           │
       └───────────┘
```

Но это всё ещё **статическая проверка**.

И вот тут начинается вторая половина истории.

# 5. Почему одного BSL LS недостаточно

Представь, агент изменил форму документа.

BSL LS говорит:

```text
0 diagnostics
```

Но при запуске:

* поле не появилось из-за функциональной опции;
* кнопка существует, но скрыта правами;
* обработчик назначен не тому элементу;
* табличная часть пустая;
* форма падает только после выбора организации;
* СКД синтаксически правильна, но выдаёт неправильные данные;
* клиент-серверный вызов ломается лишь в реальном runtime.

То есть агент должен сделать то, что делаешь ты:

```text
запустить 1С
     ↓
открыть документ
     ↓
заполнить поля
     ↓
нажать кнопку
     ↓
посмотреть результат
```

И именно здесь появляются **Answer42 и Vanessa**.

# 6. Answer42 — «глаза и руки агента в живой 1С»

В Telegram-чате это сформулировали очень удачно:

**Answer42 — лёгкая проверка во время разработки; Vanessa — тяжёлая полноценная регрессия.**

Wiz писал, что Answer42 ему нравится как простой способ **дать агенту проверить форму непосредственно в development loop**, тогда как для полного сценария и регрессии лучше Vanessa. 

Сейчас описание Answer42 это хорошо подтверждает.

Через штатный Test Client агент может:

* узнать, какая форма открыта;
* прочитать элементы формы;
* увидеть таблицы;
* нажимать кнопки;
* вводить значения;
* выбирать элементы;
* открывать списки;
* формировать отчёты;
* читать сообщения 1С;
* делать скриншоты;
* собирать **evidence report**. ([Инфостарт][5])

Получается:

```text
Codex
 │
 │ изменил BSL/XML
 ▼
запустил 1С
 │
 ▼
Answer42 MCP
 │
 ├─ открыть Документ.Реализация
 ├─ создать
 ├─ Организация = ...
 ├─ добавить товар
 ├─ провести
 ├─ проверить сообщение
 ├─ проверить таблицу
 └─ screenshot
```

Это для агента огромный скачок.

Он перестаёт говорить:

> «Я реализовал изменение.»

И начинает говорить:

> «Я реализовал изменение. Открыл Реализацию, создал документ, добавил строку товара, провёл. Форма не выдала ошибок, движение появилось. Вот состояние формы/скриншот.»

Вот это уже **proof of work**.

# 7. Vanessa — следующий уровень: сценарий бизнеса целиком

Но Answer42 хорошо подходит для проверки:

> «кнопка появилась?»
> «форма открывается?»
> «отчёт строится?»
> «после нажатия получилось X?»

А реальные ошибки 1С часто возникают в цепочке:

```text
НСИ
 ↓
Заказ клиента
 ↓
Реализация
 ↓
Счет-фактура
 ↓
движения
 ↓
закрытие месяца
 ↓
отчёт
```

Вот здесь сильнее **Vanessa Automation**.

В чате возник как раз вопрос:

> Что делать, если перед тестируемой операцией надо создать 5–6 документов?

Ответ Леонида Паутова: они используют **эталонные базы с уже подготовленными тестовыми данными**, а сам тест создаёт только то, что относится непосредственно к проверяемому поведению. Документы, которые не меняются, можно заранее держать непроведёнными и провести их во время сценария. Он также писал, что таких эталонных баз у них несколько десятков, разделённых по зонам ответственности. 

Это очень зрелая идея.

Не делать каждый раз:

```text
создай организацию
создай склад
создай валюту
создай договор
создай номенклатуру
создай остатки
создай ...
```

а взять:

```text
TestBase_Продажи
   │
   ├── организация уже есть
   ├── склад уже есть
   ├── товары уже есть
   ├── остатки уже есть
   └── необходимые документы подготовлены
```

и проверять **дельту поведения**.

## 8. Vanessa теперь тоже уже может управляться агентом

Это тоже важное изменение.

У современной Vanessa Automation есть собственная MCP-поверхность. Среди доступных инструментов есть, например:

* `check_syntax`;
* `execute_form_actions`;
* `get_active_window_data`;
* `get_form_analysis`;
* `get_form_element_data`;
* `get_table_data`;
* `run_scenario`;
* `get_test_results`;
* screenshots;
* управление test client;
* breakpoints;
* переменные и т.д. ([GitHub][6])

То есть агент уже может не просто **написать `.feature`**, а потенциально:

```text
создать сценарий
     ↓
загрузить его в Vanessa
     ↓
запустить
     ↓
получить failed step
     ↓
посмотреть форму
     ↓
исправить код
     ↓
перезапустить
```

И это уже полноценный feedback loop.

# 9. А YAxUnit — другой уровень тестирования

YAxUnit — это скорее тестирование **программной логики**, а не прохождение UI-процесса.

Условно:

```text
Функция РассчитатьСкидку(...)
```

можно протестировать:

```text
дано X
ожидаем Y
```

или проверить записи/движения/данные.

Он умеет запускаться из EDT, конфигуратора, предприятия и командной строки, а результаты выдавать в JUnit/JSON/Allure, то есть его вполне можно встроить в автоматический pipeline. ([Bia Technologies][7])

В чате писали интересную вещь: сам YAxUnit агенту подключить не слишком сложно; проблема была в другом — **агенты не умеют эффективно им пользоваться**, начинают тупить, делать слишком много действий и жечь огромное количество токенов. Решение участники видели в специальных skills: анализировать, где агент ошибается, и буквально обучать его правильной процедуре тестирования. 

Это очень похоже на то, что мы обсуждали про твои skills.

# 10. В итоге получается почти идеальный стек для AI-разработчика 1С

Я бы сейчас нарисовал его вот так:

```text
                    ТЗ
                     │
                     ▼
                Planner LLM
                     │
             понять конфигурацию
                     │
         ┌───────────┴────────────┐
         ▼                        ▼
  code-index-mcp            rlm-tools-bsl
 структурные связи        сложное исследование
         │                        │
         └───────────┬────────────┘
                     ▼
                   Unica
          metadata / forms / SKD
          BSL / roles / editing
                     │
                     ▼
                 изменить код
                     │
                     ▼
             BSL Language Server
                     │
            static validation
                     │
                     ▼
                 build/update
                     │
                     ▼
                   1С
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
      YAxUnit     Answer42    Vanessa
         │          │           │
      unit       smoke/UI    full scenario
      logic       check       regression
          └──────────┼──────────┘
                     ▼
              evidence/result
                     │
             ┌───────┴──────┐
             │              │
           PASS            FAIL
             │              │
             ▼              ▼
            done        agent fixes
                           │
                           └── loop
```

И вот **это**, на мой взгляд, самое интересное в том AI+1С-чате.

Они фактически перестали обсуждать вопрос:

> «Какая модель лучше пишет 1С?»

и начали решать более правильную задачу:

> **«Как построить окружение, в котором даже несовершенная модель сможет найти нужный код, понять конкретную конфигурацию, изменить её, проверить себя статически, запустить настоящую 1С и доказать, что изменение работает?»**

Для `1C-Migration-Lab` я бы поэтому сейчас особенно внимательно сравнил **Unica vs `rlm-tools-bsl` vs твой `code-index-mcp`**, а отдельно сделал карту **Answer42 vs Vanessa MCP vs YAxUnit**. Там вполне может оказаться, что значительную часть того самого «AI-помощника для огромной конфигурации 1С», который ты задумал ещё давно, **уже не надо писать с нуля — надо правильно собрать существующие части в один контур**.
