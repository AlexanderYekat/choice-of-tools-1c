## Вход пользователя

Собрать из существующих open-source компонентов максимально эффективный
AI-инструментарий для программиста 1С:Предприятие 8, пригодный для реальной
разработки с управляемыми формами. Обычные формы не обязательны. Хост
агента не обязан быть Cursor. Нужен не набор из десятков одновременно
подключённых MCP/skills и не монолит, а минимальный и хорошо
спроектированный контур, позволяющий coding-agent'у: исследовать большие
существующие конфигурации 1С без загрузки значительной части конфигурации
в контекст; находить BSL-код, определения, использования, callers/callees,
обработчики событий, подписки, работу с регистрами и другие связи; понимать
метаданные, управляемые формы и связанные с ними модули; по необходимости
получать точную справку по языку BSL и API платформы 1С; вносить изменения
в BSL, формы, метаданные и другие исходники там, где это технически
возможно; выполнять статическую проверку изменений; обновлять/собирать
конфигурацию и запускать 1С; выполнять целевую runtime/UI/автоматизированную
проверку сделанных изменений; возвращать агенту компактные структурированные
результаты и evidence вместо больших логов, исходников и сотен результатов
поиска. Ключевой критерий — эффективность контекста. Нужна архитектура с
небольшой стабильной внешней поверхностью (фасад) и более богатым внутренним
набором. Выбранный состав: Unica, code-index-mcp (`bsl-indexer`),
v8-runner, Answer42, Vanessa Automation. Стыковка с фасадом ещё
не исследована. Контур не для всех репозиториев; в одном 1С-проекте
допустимы несколько информационных баз.

Машинная запись: [request.json](request.json). Дословный вход v1 — в
снимке `history/goal-v1/request.json` (читать только если нужен старый
критерий).

## Результат и сценарии

Желаемый наблюдаемый результат: обоснованный минимальный набор существующих
компонентов (и тонкий собственный фасад поверх них), из которого можно
собрать контур агента для разработки 1С 8. Не набор из десятков MCP/skills
и не монолит. Состав выбран; готовность внедрения наступает после проверки
стыковки, не сейчас.

Пользовательские сценарии:

1. Агент исследует большую незнакомую конфигурацию и находит нужные объекты и
   связи, не загружая конфигурацию в контекст.
2. Агент находит определение и использования процедуры/функции BSL, обработчики
   событий, подписки и обращения к регистрам.
3. Агент получает точную справку по синтаксису BSL и API платформы по
   конкретному вопросу.
4. Агент вносит изменение в модуль управляемой формы, метаданные или общий
   модуль.
5. Агент выполняет статическую проверку изменений и получает компактный список
   замечаний.
6. Агент обновляет/собирает конфигурацию, запускает 1С и выполняет целевую
   runtime/UI-проверку.
7. Агент получает компактный структурированный результат проверки и исправляет
   ошибку в цикле.
8. В одном проекте агент работает с двумя информационными базами (стороны
   обмена), не считая их одной «текущей 1С».

Текущее состояние: обзор 19 выполнен; контур выбран на бумаге; фасад
описан как методика; ничего не установлено. Избегать разработки с нуля:
индекс/парсер BSL и метаданных, база справки платформы, движок статического
анализа BSL, движок сборки/запуска 1С, движок UI/функционального тестирования.

## Критерии

Категории те же, что в v1. ID не перенумеровывались. Деление
explore/docs/edit/verify/debug — рабочая гипотеза фасада, не обязательный
внешний API.

### C1 — Исследование больших конфигураций без загрузки в контекст

Обязательное. Успех: поиск сначала сужает пространство кандидатов и возвращает
краткие структурированные результаты, а не десятки файлов или полный исходный
код. Эталон: сценарий 1. Вопрос: есть ли индекс/сервис вне окна контекста и
отдельный шаг read фрагмента?

### C2 — Навигация по связям BSL

Обязательное. Успех: находятся определения, использования, callers/callees,
обработчики событий, подписки, обращения к регистрам и сопоставимые связи.
Эталон: сценарий 2. Вопрос: какие именно виды связей реализованы в коде, а не
только заявлены?

### C3 — Метаданные и формы

Обязательное для **метаданных и управляемых форм**. Обычные формы **не
обязательны** (в цели v1 были обязательны наравне; см.
[GOAL-CHANGE.md](GOAL-CHANGE.md)). Успех v2: инструмент понимает метаданные,
управляемые формы и связанные модули. Пробел `Form.bin` / ordinary XML не
блокирует контур. Вопрос: какой формат выгрузки и какие типы форм реально
разобраны?

### C4 — Точная справка по BSL и API платформы

Обязательное, по запросу. Успех: агент получает ответ по конкретному языковому
или платформенному вопросу без загрузки всей документации в контекст.
Эталон: сценарий 3.

### C5 — Изменение исходников 1С

Обязательное. Успех: можно вносить изменения в BSL, управляемые формы,
метаданные и другие исходники там, где это технически возможно. Эталон:
сценарий 4. Обычные формы не входят в успех.

### C6 — Статическая проверка изменений

Обязательное. Успех: после правки доступна статическая проверка с компактным
списком замечаний. Эталон: сценарий 5.

### C7 — Обновление, сборка и запуск 1С

Обязательное. Успех: конфигурацию можно обновить/собрать и запустить 1С из
контура агента. Эталон: сценарий 6, первая половина.

### C8 — Целевая runtime / UI / автоматизированная проверка

Обязательное. Успех: сделанные изменения проверяются точечно (тест, UI-сценарий
управляемого приложения, вызов в ИБ), а не только «конфигурация открылась».
UI обычных форм не требуется. Эталон: сценарии 6–7. Предложенные UI-слои
Answer42 (r20) и Vanessa (r21) в обзоре 19 не аудированы; в активном
реестре — NOT_CHECKED / PENDING.

### C9 — Компактные структурированные результаты

Обязательное. Успех: большие выдачи имеют фильтрацию, группировку,
pagination/narrowing или чтение выбранного фрагмента; агенту возвращается
evidence, а не сырые логи.

### C10 — Минимальная внешняя поверхность и progressive disclosure

Обязательное. Успех: агент постоянно видит небольшую стабильную поверхность;
подробности подключаются только когда нужны. В v2 это свойство фасада, не
сырого объединения MCP.

### C11 — Знания вне окна контекста

Предпочтение. Успех: индексы, документация, результаты анализа и промежуточные
артефакты живут в файлах/БД/сервисе и возвращаются по запросу.

### C12 — Независимость 1С-логики от способа подключения агента

Предпочтение. Успех: работа с 1С отделена от MCP/CLI/конкретного хоста;
Cursor не критерий успеха. Одна capability не реализуется несколько раз.

### C13 — Замкнутый feedback loop

Обязательное как свойство контура. Успех: исследование → изменение →
статическая проверка → обновление/запуск → целевая проверка → компактный
результат → исправление.

### C14 — Отсутствие ненужного дублирования

Предпочтение. Успех: если два инструмента закрывают одну capability, выбран
основной. rlm не дублирует выбранный explore; skills Cursor/Claude не
дублируют Unica; r09 METR не дублирует выбранный r22.

## Решения, ограничения и предположения

Решения пользователя (v2; v1 — в снимке):

- не писать с нуля то, что уже качественно реализовано;
- внешняя tool surface минимальна и стабильна;
- обычные формы не обязательны;
- хост не обязан быть Cursor;
- состав: Unica, code-index-mcp, v8-runner (r22), Answer42, Vanessa
  и тонкий фасад; r09 METR не в контуре (решение 2026-09-21);
- rlm и skills Cursor/Claude не в контуре;
- 1С-проект — по существующим признакам/структуре; манифест опционален;
- состав выбран, внедрение рано до стыковки;
- не каждый репозиторий — 1С; несколько ИБ в одном проекте допустимы;
- план стыковки фиксируется отдельно; этим шагом пять продуктов не
  читаются заново и не устанавливаются.

Ограничения: Windows 10/11; coding-agent с MCP/CLI; open-source;
существующие большие конфигурации; на шаге плана только файлы
исследования.

Нежелательные зависимости: те же, что в v1 (свой парсер, справка,
анализатор, сборка, UI-движок).

Неизвестно: рабочие конфигурации, наличие EDT, лицензии платформы,
формат выгрузки, готовность ставить расширения в ИБ, точный набор
признаков автоопределения 1С-проекта (уточняется на аудите стыковки).

Предположения:

- A1: исходники доступны как файловая выгрузка (XML конфигуратора и/или
  EDT).
- A2: хост агента не фиксирован; наличие MCP/CLI влияет на адаптер, не на
  ядро 1С-логики (C12).
- A3: деление explore/docs/edit/verify/debug — рамка фасада, не
  обязательные внешние имена.
- A4: «как библиотека/core» допустимо, если родной MCP слишком широкий.
- A5: 1С-проект по умолчанию узнаётся по уже существующим признакам
  (например `v8project.yaml`, `Configuration.xml`, EDT `.mdo`) — точный
  список не утверждён без аудита. Новый манифест не обязателен для любого
  1С-проекта; он для явной конфигурации нескольких sources/targets.
