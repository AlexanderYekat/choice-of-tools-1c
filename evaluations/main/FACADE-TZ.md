## 1. Цель и нефункциональная рамка

Источник: [request.json](request.json), [BRIEF.md](BRIEF.md) (C1–C14).

Агент должен видеть **малую стабильную внешнюю поверхность** (ориентир
5–8 операций), не сырой `tools/list` пяти продуктов (десятки–сотни
записей). Внутри фасада — пять готовых движков, ни один не переписывается
с нуля:

- собственный индекс/парсер BSL — не писать;
- собственная база справки BSL/API — не писать;
- собственный статический анализатор — не писать;
- собственный движок сборки/запуска 1С — не писать;
- собственный UI/функциональный движок — не писать.

Ключевой критерий — эффективность контекста (`success_criteria[0]`):
у цикла работы агента должен быть измеримый и небольшой бюджет байт/строк
в чате. Это проверено (раздел 8), не блокер при выполнении обязательных
условий.

## 2a. Инфраструктурная опора: v8-harness

Решение 2026-09-22, по итогам исследования репозитория
`https://github.com/AlexanderYekat/v8-harness` (владелец — пользователь
этого запуска; локальный клон совпадает с `origin/master`,
`105b3aa4f16…`, HEAD на момент решения; та же связка уже подключена
в этом самом запуске как opt-in fixture, `AGENTS.md` этого репозитория:
«Обвязка 1С — opt-in: маркер `v8stands.yaml`»).

**Что это.** Тонкая обвязка (935 строк, только stdlib Python 3.10+,
19 unit-тестов) вокруг `v8-runner`. Не MCP, не сетевой сервис — CLI
поверх subprocess. Решает ровно одну проблему: у `v8-runner` один
`v8project.yaml` = одна ИБ, без понятия «несколько именованных целей
в одном проекте» и без связи с уже существующим списком баз 1С.
Harness добавляет: именованные `stands` в одном маркер-файле
`v8stands.yaml`; адресацию ИБ по имени из `ibases.v8i` (`from:
launcher`), по пути файловой ИБ (`from: file`), по строке подключения
(`from: connection`) или из `.cf` в новую файловую ИБ (`from: cf`);
генерацию `.v8/stands/<id>/v8project.yaml` + отдельного
`v8project.local.yaml` с секретами (пароль запрещён в самом
`v8stands.yaml` — `load_stands` explicit отказ); условную загрузку
Vanessa/YaXUnit (`download-tools`) только если включено флагом;
регистрацию файловых ИБ в списке запуска 1С (`register`), без
дублей по `Connect`/`ID`.

**Чего это не делает.** Не трогает Unica, code-index-mcp или Answer42
— работает только со слоем `r22`(build/static/verify.unit) и
транспортом Vanessa (`test va`). Не поднимает MCP/stdio-сервер, не
формирует единый envelope/таксономию ошибок, не занимается бюджетом
контекста и артефактами — это всё остаётся задачей самого фасада,
harness не заменяет его архитектуру целиком.

**Решение: взять за основу для слоя ConfigLoader/TargetRegistry в
части r22/Vanessa**, не переписывать этот кусок заново. Соответствует
принципу «не писать с нуля то, что уже качественно реализовано»
([DECISION.md](DECISION.md)) — конфиг-генератор и реестр стендов уже
реализованы, протестированы и уже используются в этом самом запуске.
Не заменяет остальную архитектуру фасада (Router, остальные 4
адаптера, envelope, ArtifactStore, бюджет контекста) — closes только
часть вопросов [FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md) §3.

Технические следствия — в §6, §14 (пп. 1–3) ниже и в
[FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md).

## 3. Внешняя поверхность (что видит агент)

Источник: [FACADE.md](FACADE.md) раздел «Внешняя поверхность»,
подтверждено прогоном E3 ([logs/e3-chain-simple.md](logs/e3-chain-simple.md)).

```
(только если корень распознан как 1С-проект)

explore                 → code-index-mcp / bsl-indexer   (+ source)
docs                    → Unica
edit.view / edit.apply  → Unica                          (apply — явно, не по умолчанию)
static                  → Unica и/или синтаксис r22
verify.unit             → r22 + YaXUnit                  (+ target)
verify.form             → Answer42                       (+ target)
verify.scenario         → Vanessa через r22 test va       (+ target, опционально peer)
```

Правило разведения verify (из [DECISION.md](DECISION.md)):

1. правка общего модуля / серверной логики → `verify.unit` (YaXUnit через `r22`);
2. «форма открылась / кнопка нажалась / поле заполнилось» → `verify.form` (Answer42);
3. цепочка документов или регрессия → `verify.scenario` (Vanessa через `r22`).

Слои не подменяют друг друга: Unica — не основной поиск по графу
(`unica` call graph на поверхности v0.13 отсутствует); Answer42 — не
основной индекс исходников (RAG не брать как explore); `r22` — не
библиотека шагов Vanessa, а её транспорт запуска.

Нет бэкенда или нет живой базы для конкретной операции — она обязана
ответить «недоступно, причина», а не пропасть молча и не подменить
соседний слой.

## 4. Контракт адресации цели

Обязательное правило для всех операций verify/edit/static, подтверждено
E2 ([logs/r01-r22-e2-two-targets.md](logs/r01-r22-e2-two-targets.md)):
агент работает с **именем цели**, никогда с «текущей единственной 1С».
Молчаливый дефолт на «текущую» базу — отказ приёмки.

- **Unica**: адресация `at="<source-set>:<путь>"` внутри одного
  `v8project.yaml` с несколькими `CONFIGURATION source-set`. Подтверждено
  живьём: `at="main:…"` и `at="cf220:…"` резолвятся раздельно к разным
  payload, `at="bogus:…"` даёт именованный `provider_unavailable`, а не
  тихий откат на `main`. **Обнаруженное ограничение**: путь
  `source-set.path` обязан быть workspace-relative и не выходить за
  корень workspace — абсолютные пути Unica отклоняет как невалидный yaml.
  Если у двух целей нет общего каталога-предка внутри одного workspace,
  единый `v8project.yaml` для обеих физически невозможен без временного
  файла на корне репозитория (как это обойдено в E2a — временно и с
  удалением после прогона, не решение для продакшна фасада).
- **v8-runner (`r22`)**: одна yaml — одна ИБ; две цели — два процесса
  с разными `--config`. Подтверждено: операция на цели A не меняет
  sha256 `1Cv8.1CD` цели B; несуществующий `--config` — явный
  `invalid_argument`, без отката на дефолтный проект. **С v8-harness
  (§2a) вместо ручной сборки `--config` — именованный `stand` в
  `v8stands.yaml`**: `target` фасада = stand id, harness сам генерирует
  и держит `.v8/stands/<id>/v8project.yaml`, фасад зовёт `v8-harness
  run --stand <id> -- <r22-аргументы>` (или импортирует
  `runner_command()` как библиотеку). Модель «одна yaml — одна ИБ» не
  меняется, меняется только то, кто её пишет и именует.
- **Answer42 (`r20`)**: `session_id` — обязательный ключ цели, дубль
  `session_id` отказан явно; два `base_url` на одном stdio MCP дают два
  живых независимых окна (dual live PASS).
- **Vanessa (`r21`)**: адресация через `r22 test va` (тот же
  `--config`/target, что и остальной `r22`). Одновременность двух
  активных Test Client Vanessa **не проверена — UNKNOWN осознанно**,
  контракт фасада держит `target -> profile/connection` однопоточным
  для этого слоя, пока не появится отдельная проверка.

## 5. Контракт по операциям

Для каждой операции: продукт и вызов, вход, известный выход/размер,
обязательные файловые артефакты, подтверждённые отказы.

### 5.1 `explore`

- Продукт: `r15`, CLI ядра (`bsl-indexer`) или stdio/HTTP MCP c
  `[tools].enabled`.
- Вход: alias каталога выгрузки (`--path alias=dir` / `[[paths]]`),
  запрос (имя функции/объекта).
- Пример: `search-function РассчитатьСумму` → 3202 байт / 66 строк
  (E3, шаг 1) — можно целиком в чат.
- Узкая поверхность подтверждена: без `[tools].enabled` живой
  `tools/list` = 33 (13 1С-tools + core); с whitelist — 9 из заданного
  подмножества, вне списка `-32602` (и на HTTP, и на stdio, идентично —
  E4). CLI не показывает `tools/list` вовсе.
- Несколько выгрузок — несколько alias, отдельный `index.db` на каждую;
  явный `source` обязателен, смешивания без него не подтверждено и не
  ожидается.

### 5.2 `docs`

- Продукт: `r01` Unica, `unica.docs`.
- **Асинхронная операция**: ответ — тикет задачи (`status: queued/working`),
  не результат. Финальные данные — через `unica.task.result` с опросом,
  **в том же жизненном цикле демона/state-dir**, что исходный вызов;
  разный `UNICA_PROVIDER_STATE_DIR` для старта и опроса даёт
  `task_transport_failed`. Фасад обязан удерживать один provider-state на
  всю пару «начать — опросить».
- Размер (E3, шаг 2, запрос «НаборЗаписей»): **77 205 байт / 800 строк**,
  5 секций / 80 hits — **обязательно в файл**, в чат — только summary
  и путь. Это единственная не-бинарная операция с обязательной выгрузкой.

### 5.3 `edit.view` / `edit.apply`

- Продукт: `r01` Unica.
- `view {at}` — 3260 байт / 86 строк (E3, шаг 3) — можно в чат, но
  близко к порогу, если объект крупнее.
- `apply` — **явный** вызов, не по умолчанию (принцип 7 из FACADE.md:
  разрушительное — явно, с именем цели).
  - `dryRun:true` — 1616 байт / 59 строк (E3, шаг 4), план `preview`+`rev`.
  - `dryRun:false` обязан идти с `ifRev`; без него публикация отвергается;
    stale `ifRev` — явный `stale_revision`, не молчаливая перезапись.
- **Формат выгрузки — стык, не деталь.** Unica читает дамп формата 1.0
  свободно (`view`, `docs`), но отказывает любой операции записи
  (`apply`, `check`) на нём: `"export format 1.0 is older than the
  writable profile 2.20 for 1C 8.3.27; re-export the sources with the
  platform before editing them"`. **Фасад не может считать один и тот же
  `source-set` одновременно источником explore/docs и целью edit/static,
  если это разные по формату дампы — это нужно явно развести в конфиге
  цели**, не угадывать.

### 5.4 `static`

- Продукт: `r01 unica.check` и/или `r22 syntax designer-modules`.
- `unica.check {at}` на cf220: 568 байт / 23 строки. `r22 syntax
  --server --thin-client`: 484 байт / ~20 строк. Оба — в чат целиком.
- `unica.check` на дампе формата 1.0 отвечает `source_unreadable` —
  тот же стык формата, что в 5.3.

### 5.5 `verify.unit`

- Продукт: `r22` CLI + YaXUnit, конверт `--json-message`
  (`ok`, `data.report`, `data.retained_paths`).
- Размер честного прогона (даже неудачного): 5304 байт / 118 строк
  (E3, шаг 7) — в чат целиком.
- **Открытый риск, не готово к фасаду.** Подробности — раздел 9.
- Стык: `v8-runner` резолвит имя расширения **по имени `source-set` в
  yaml**, не по фактическому `Name` объекта в самой ИБ — рассинхрон даёт
  «не найдено» при полностью активном расширении. Имя `source-set` в
  конфиге цели обязано совпадать с реальным именем объекта в ИБ.
- Стык: incremental `build` не всегда надёжен после насыщенной серии
  пересборок расширений (`"Ошибка чтения файла-списка загружаемых
  файлов"`); фасаду нужен fallback на `--full-rebuild`, а не одна попытка
  incremental сборки.

### 5.6 `verify.form`

- Продукт: `r20` Answer42, stdio MCP, `--tool-profile ui --disable-rag`.
- `start_session` — 9960 байт / 191 строка (на грани, лучше выдержка,
  не сырой ответ целиком); `active_window` — 2752 байт / 52 строки (в
  чат); `screenshot` — 1008 байт JSON + **180 197 байт PNG** (E3, шаг 8).
- **PNG — только файл, путь в JSON, никогда не инлайнить.** Это уже
  сделано правильно продуктом (путь, не base64), фасаду достаточно
  передать путь дальше.
- Живой `tools/list` при `ui`+`--disable-rag` = 103 (статический `full` —
  122) — фасад всё равно обязан сузить дальше, до подмножества операций
  из раздела 3.

### 5.7 `verify.scenario`

- Продукт: `r21` Vanessa, запуск через `r22 test va` (не сырой
  `1cv8 /Execute` фасада).
- Размер: 3964 байт / 110 строк (E3, шаг 9) — в чат целиком.
- MCP Vanessa (37 tools статически) — для интерактивной отладки, не
  основной путь `verify.scenario`.

## 6. Определение 1С-проекта

Источник: [FACADE.md](FACADE.md) «Когда фасад молчит», подтверждено
частично S5 ([VALIDATION.md](VALIDATION.md)); пересмотрено 2026-09-22
по факту v8-harness (§2a).

**Пересмотр, не первоначальный дефолт.** Методология изначально
предполагала автоопределение по структурным признакам
(`Configuration.xml`/EDT `.mdo`) как основной путь, манифест —
опционально. v8-harness, уже принятый за основу для конфигурации
(§2a), явно и намеренно делает наоборот: «Не подключай обвязку только
потому, что в проекте есть конфигурация 1С» ([SKILL.md v8-harness],
[AGENTS.md v8-harness]). Это уже действующая политика в этом самом
репозитории (`AGENTS.md`: «Обвязка 1С — opt-in: маркер
`v8stands.yaml`»), не гипотеза. Фасад наследует ту же политику вместо
собственной автоэвристики — меньше кода, меньше риска ложного
срабатывания на репозитории, где 1С-артефакты есть, но агенту в них
лезть не просили:

- **По умолчанию — молчание.** 1С-операции не регистрируются, пока
  в корне нет `v8stands.yaml` (расширенного фасадом — §14 п.2) или
  пользователь явно не попросил его завести (`attach`-подобный шаг).
  Присутствие `Configuration.xml`/`.mdo` само по себе — не триггер.
- **Единственный признак включения — маркер-файл.** Не список
  эвристик, одна проверка: файл есть → фасад читает `stands`/`sources`
  из него и регистрирует ровно то, что там названо. Файла нет — фасад
  не регистрирует 1С-операции вовсе, независимо от структуры каталога.
- В воркспейсе с несколькими корнями — маркер ищется и действует
  только в том корне, где лежит; соседний корень без маркера не
  затрагивается.
- Секреты — не в маркер-файле (`v8stands.yaml` явно отказывает при
  ключе `password` — уже in the product), а в генерируемом
  per-stand `v8project.local.yaml`, не в git, не в чат, не в аргументы
  MCP-вызова. Подробности — §14 п.3.

## 7. Несколько целей в одном проекте

Типовой случай — обмен: две ИБ, иногда две выгрузки. См. раздел 4 для
контракта адресации. Дополнительно, из E2:

- фасад не обязан сам реализовывать протокол обмена;
- фасад обязан позволить указать `target` (и пару `target`/`peer`) на
  verify-операциях;
- фасад не должен смешивать индексы двух выгрузок без явного `source`;
- если продукт умеет только одну сессию — мягкий минус, фасад держит две
  сессии снаружи или запускает продукт дважды с разным контекстом; не
  обязательно, чтобы продукт «из коробки» знал про обмен.

## 9. Семь обязательных стыков между продуктами

Каждый пункт — не наблюдение, а требование к поведению фасада.

1. **Формат 2.20 vs 1.0.** Источник explore/docs и цель edit/static —
   разные дампы по умолчанию, если формат рукописной/старой выгрузки не
   2.20. Фасад обязан явно развести `source` (чтение) и `target`-дамп
   (запись), не предполагать один и тот же путь для обеих ролей.
2. **Владелец ИБ.** Только `r22` создаёт/грузит файловую ИБ
   (`init`/`build`/`load`). Unica не трогает ИБ напрямую — только
   XML-дамп на диске. Правка через Unica не попадает в живую ИБ без
   отдельного шага `r22 build` поверх отредактированного дампа — это два
   разных продукта с разделённой ответственностью, фасад обязан явно
   провести этот шаг, не подразумевать его автоматическим.
3. **Владелец рабочего дампа.** `.v8/work/<...>` (снимок `r22 dump`) —
   производный артефакт, не альтернативный источник истины. Несёт следы
   предыдущих операций (например `Comment` от публикации). Повторный
   `dump` затирает такие следы молча. Фасад обязан либо снимать рабочие
   дампы в новый каталог на каждый цикл, либо явно логировать
   перезапись перед действием.
4. **Имя расширения у `r22` — по `source-set`, не по объекту.**
   `extensions`/`dump --extension`/`load --extension` резолвят цель по
   имени `source-set` в yaml, а не по фактическому `Name` в ИБ.
   Рассинхрон даёт ложное «не найдено» при активном расширении. Имя
   `source-set` в конфиге цели обязано совпадать с реальным именем
   объекта.
5. **`--sources` YaXUnit несовместим с `format: DESIGNER`-проектом.**
   `tools download yaxunit --sources` даёт EDT-слой исходников, не
   грузящийся в DESIGNER-проект; для такого стенда работает только
   скомпилированный `.cfe` через `load`/`merge`.
6. **Асинхронность `docs`.** См. 5.2 — один provider-state на пару
   «начать — опросить».
7. **Ненадёжность incremental build.** См. 5.5 — fallback на
   `--full-rebuild`.

## 10. Открытый риск: `verify.unit` через YaXUnit (E1)

Источник: [logs/r22-yaxunit-e1tests-simple.md](logs/r22-yaxunit-e1tests-simple.md),
claims `c22-yaxunit-crossext-discovery-unresolved-simple`,
`c22-yaxunit-crossext-hypotheses-ruled-out-simple` в
[EVIDENCE.json](EVIDENCE.json).

**Факт:** движок YaXUnit и рукописное тестовое расширение реально
установлены и активны на стенде `simple` (build/load/merge/SafeMode —
все шаги PASS), но `test yaxunit` находит 0 сценариев. Платформа не
резолвит модуль стороннего расширения (`ТестыE1`) ни статически, ни
динамически при вызове изнутри соседнего расширения (`YAXUNIT`) —
`"Метод объекта не обнаружен"`. Воспроизведено и для настоящего
`ИсполняемыеСценарии`, и для тривиального пробного метода.

**Проверено и исключено:** порядок/приоритет расширений (по документации
это только очередь `&Перед/&После/&Вместо`, не видимость),
`filter.extensions` в `config.json` YaXUnit, алфавитное имя расширения,
момент пересборки после переименования.

**Не проверено (следующие шаги, если возобновлять изоляцию):** тестовое
расширение, собранное настоящим Дизайнером/EDT (недоступны в среде
запуска), обращение в официальную поддержку 1С.

**Требование к фасаду:** пока причина не изолирована или не обойдена,
`verify.unit` через YaXUnit **не считать готовым слоем**. Фасад обязан
уметь честно отвечать `ok=false` с диагностикой на этом шаге (как это
уже делает `r22`-конверт), а не скрывать отказ и не подменять его другим
слоем verify. Это не блокирует `verify.form`/`verify.scenario` —
они закрыты независимо (Answer42, Vanessa/r22 — PASS).

## 11. Нефункциональные принципы (обязательны к соблюдению)

Источник: [FACADE.md](FACADE.md) раздел «Принципы», подтверждены
прогонами E1–E4, не пересмотрены:

1. Включение по проекту, не глобально и не из чата — признак в файлах
   проекта.
2. Один проект — несколько именованных целей (выгрузка/ИБ/сторона
   обмена), не «единственная база навсегда».
3. Неполный набор допустим: нет Vanessa — живут поиск и правки; нет
   живой 1С — нет form/scenario, остальное работает.
4. Большое — на диск, в чат — коротко (раздел 8 даёт конкретные пороги).
5. Сначала адаптер, потом патч/форк чужого репозитория.
6. Хост агента не диктует ядро (Codex/Claude/Cursor/CLI — разные адаптеры
   к одним и тем же операциям).
7. Разрушительное — явно: запись в исходники, загрузка в ИБ, проведение
   документов, прогон на «не тестовой» базе — с именем цели, без
   молчаливого дефолта на прод.

## 12. Чего фасад не делает

- не пишет свой парсер/индекс BSL, справку платформы, движок сборки,
  UI-движок — весь список раздела 1;
- не подключает пять MCP как есть агенту (сырой `tools/list` — отказ
  приёмки, C10);
- не требует Cursor как хост (C12);
- не требует обычных форм (`Form.bin` — не блокер v2, C3);
- не реализует сам протокол обмена между ИБ (раздел 7);
- не переписывает продукт «под монолит» — порядок доработки: 1) принять
  CLI/MCP как есть → 2) адаптер (рабочий каталог, обрезка JSON, subset
  tools, два процесса, свои имена целей) → 3) точечный патч/форк, с
  записью зачем, только если совсем не стыкуется.

## 13. Критерии приёмки первой версии фасада

Сопоставление с C1–C14 ([BRIEF.md](BRIEF.md)). Отметка `RUN` — операция
уже подтверждена живым прогоном отдельного продукта (не фасада);
`PROPOSED_INTEGRATION` — связь между слоями описана на бумаге, код-обёртка
ещё не существует, `VERIFIED_INTEGRATION` для фасада нет ни по одному
пункту.

| C* | Что проверяет приёмка | Текущее состояние |
|---|---|---|
| C1/C2 explore | `explore` сужает пространство, не выгружает файлы целиком | r15 CLI+MCP+whitelist RUN на `simple` |
| C3 метаданные/УФ | edit понимает метаданные и управляемые формы | r01 view/apply RUN на cf220 |
| C4 справка | `docs` отвечает по конкретному вопросу без полной документации в контекст | r01 docs RUN, но обязательна выгрузка в файл (раздел 8) |
| C5 edit | правка BSL/УФ/метаданных возможна и explicit | r01 apply dryRun+publish RUN |
| C6 static | компактный список замечаний после правки | r01 check + r22 syntax RUN |
| C7 build/run | конфигурация обновляется/собирается, 1С запускается | r22 init/build RUN; две ИБ одновременно RUN (E2b) |
| C8 runtime/UI | целевая проверка, не только «конфигурация открылась» | Answer42 RUN, Vanessa/r22 RUN; **YaXUnit — открытый риск, не PASS** |
| C9 компактные результаты | фильтрация/группировка/файл вместо сырых логов | заложено в конвертах r22/Unica, не проверено фасадом |

## 14. Открытые вопросы — дефолты

Пользователь 2026-09-22 попросил закрыть эти шесть вопросов дефолтом,
не усложняя, вместо мини-эксперимента по каждому. Ниже — рабочее
решение для старта реализации, не новый проверенный факт. Если реальность
не ляжет в дефолт — пересмотреть точечно на этом же месте, не переносить
на весь контур.

1. **Маркер включения — пересмотрено (§6, §2a): не список структурных
   признаков, а единственный opt-in файл.** `v8stands.yaml` в корне
   репозитория (расширенный, см. п. 2) — единственный триггер. Ничего
   похожего на «нашли `Configuration.xml` — включились» не делаем;
   это та же политика, что у v8-harness, уже принятая в этом самом
   репозитории ([AGENTS.md](../../AGENTS.md), корень исследования).
2. **Формат манифеста — пересмотрено: переиспользовать `v8stands.yaml`
   v8-harness, не изобретать `.v8/facade.yaml`.** Поля `tools`/`stands`/
   `platform` — как есть у v8-harness (`from: launcher|file|connection|
   cf`, `sources`, `features`, `user`). Фасад добавляет **опциональные**
   поля поверх существующей схемы (парсер v8-harness игнорирует
   незнакомые ключи — проверено по `load_stands`): `read_source` на
   стенде — отдельный путь для explore/docs, если он отличается от
   `sources` (нужен из-за стыка «формат 2.20 vs 1.0», §9 п.1); `role`
   (`test`/`dev`/`never-prod`) — для правила «verify только на
   test/dev» (раздел «Что ещё заложено» [FACADE.md](FACADE.md)).
   Ничего сверх этих двух полей не добавлять без нового случая.
3. **Credentials — пересмотрено: переиспользовать
   `v8project.local.yaml` v8-harness**, не заводить отдельный
   `.env`-файл. Это уже реализовано и работает: `v8stands.yaml`
   отказывает при ключе `password` (`load_stands`, явная проверка в
   исходнике), секрет уходит в генерируемый `.v8/stands/<id>/
   v8project.local.yaml`, не в git (харнес сам пишет `.v8/.gitignore`).
   Фасад передаёт пароль через тот же путь, что и v8-harness (`attach
   --password` при регистрации стенда, либо ручная правка local-файла
   пользователем) — не через чат, не через аргумент MCP-вызова.
4. **Source vs target-дамп при разных форматах — единая запись по
   умолчанию, разведение только по факту отказа.** Стенд `sources`
   (поле v8-harness) служит и источником чтения, и целью записи, пока
   `apply`/`check` не вернёт `invalid_source`/`source_unreadable`. После
   этого фасад требует явного `read_source` на том же стенде (новое
   опциональное поле, п. 2) для чтения и отказывает с понятным
   сообщением, какой дамп нужен для записи — не переключается сам и не
   конвертирует формат автоматически. `sources` остаётся тем, куда
   `r22` пишет по `apply`/`build`; `read_source`, если задан, — то, что
   читают `explore`/`docs`/`edit.view`.
5. **Судьба E1 — не продолжать изоляцию причины сейчас.** Первая версия
   фасада реализует `verify.unit` как честно недоступный/открытый-риск
   слой: вызов есть, ответ `ok=false` с диагностикой YaXUnit, без
   попытки скрыть отказ или молча подменить его `verify.form`/
   `verify.scenario`. Возврат к изоляции причины — отдельным решением
   пользователя, не автоматически при следующей работе с `r22`.
6. **Диагностический долг стенда — откатить перед следующим
   использованием стенда, не перед написанием кода фасада.** Простое
   правило: инструментация внутри `YAXUNIT` в `.v8/ib/simple` (см.
   [STATE.md](STATE.md)) откатывается как первый шаг перед любым новым
   экспериментом на этом стенде — для любой цели, не только E1. Само
   написание кода фасада этот долг не блокирует.
