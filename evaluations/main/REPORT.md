## Ответ для пользователя

Готового монолита среди 19 репозиториев нет. Собирать всё сразу тоже
не нужно.

**После уточнения заказчика выбранный набор записан в
[DECISION.md](DECISION.md).** Исторический вывод обзора (до уточнения)
был таким:

**Минимальный набор с наибольшей функциональностью на единицу контекста:**

1. **[rlm-tools-bsl](https://github.com/Dach-Coin/rlm-tools-bsl) (r02)** —
   explore почти без изменений: 6 MCP-tools, песочница, индекс CF/EDT,
   callers/ссылки *заявлены* в хелперах. Это лучший найденный ответ на
   «не грузить конфигурацию в контекст».
2. **[unica](https://github.com/IngvarConsulting/unica) (r01)** — основной
   facade edit / static / run / docs: ровно 11 типизированных tools,
   skills подгружаются отдельно, внутренние движки спрятаны. Официальные
   хосты — Codex и Claude; в Cursor, скорее всего, заведётся как обычный
   stdio MCP, но это не проверено. Платформа заявлена как 8.3.27.
3. **[mcp-onec-test-runner](https://github.com/alkoleft/mcp-onec-test-runner) (r09)** —
   сборка Designer/IBCMD + YaXUnit + синтаксис конфигуратора/EDT. Это
   недостающий кусок feedback loop, которого нет у Unica.

**Собственный тонкий router/facade — да, нужен**, но как адаптер, не как
новый 1С-движок. Если просто включить r02+r01+r09, агент увидит 6+11+8
tools. Слой из пяти стабильных capability (explore / docs / edit / static /
verify) должен вызывать эти продукты и класть большие выдачи в файлы.

**Обычные формы — главный незакрытый раздел.** Unica, rlm и cursor-skills
редактируют и разбирают *управляемые* Form.xml. Unica лишь *принимает*
`FormType=Ordinary` при добавлении справки. Модули обычных форм по пути
находятся, структура (часто `Form.bin`) — нет. Это нельзя вывести из
«поддержки 1С».

**Что брать как библиотеку, не как их MCP:**
- r04 `v8-context-hbk` — ядро индекса синтакс-помощника (если не хватит
  `unica.docs` / r10). Учесть внешнюю path-зависимость в Cargo.toml.
- r15 `code-index-mcp` / `bsl-indexer` — если понадобится персистентный
  граф вместо sandbox r02; не светить 30 tools.
- выбранные скрипты r12 — fallback edit в Cursor, если Unica не
  подключается.

**Что не включать в повседневный набор:** r05, r08, r11, r13 (дубль r12),
r14, r16, r18, r19. **Спецслучаи:** r06 (REST в ИБ), r07 (CI install),
r17 (только EDT), r15 как альтернатива explore.

Недостаёт: ordinary-form structure, UI-проверка обычных форм, verified
call graph, проверенное подключение Unica к Cursor.

Следующий шаг — не писать помощника, а одним экспериментом проверить
либо Unica MCP в Cursor, либо качество explore r02 на выгрузке с обычной
формой (см. [VALIDATION.md](VALIDATION.md)).

## Цель и охват

Критерии C1–C14 — [BRIEF.md](BRIEF.md). Входов 19, уникальных 19,
недоступных 0, дубликатов URL 0. r12 и r13 — содержательно один toolkit
в двух упаковках. Карточки: [reports/](reports/).

Обзор, не deep-static: списки tools r09 (8 `@Tool`) и 1С-надстройка r15
(13 tools) закреплены по исходникам; r10 и универсальные 20 tools r15
остаются DOCUMENTATION. Авторские бенчмарки r02/r15 не принимались как
собственное измерение. r17 явно отказывает ordinary forms.

## Решения и архитектурные варианты

| Решение | Кандидаты | Условие |
|---|---|---|
| Использовать почти как есть | r02 | HTTP/stdio MCP, slim+`rlm_help` |
| Использовать как facade продукта | r01 | получится подключить в Cursor; иначе fallback |
| Использовать как verify | r09 | GPL-3.0 приемлем; есть YaXUnit |
| Как core, не MCP | r04, частично r15 | docs/граф |
| Адаптировать выборочно | r12 (router+meta/form/db) | не весь каталог скилов |
| Спецслучай | r06, r07, r17, r15-alt | по среде |
| Исключить из сценария | r05, r08, r11, r13, r14, r16, r18, r19 | дубль, не та роль, тяжесть |

**Вариант A (предпочтительный):** facade + r02 + r01 + r09.
Выигрыш: узкая идея поверхности, сильный explore, сильный edit/run, тесты.
Ограничения: Cursor/8.3.27/LGPL+GPL, ordinary forms.
Опровержение: Unica не стартует в Cursor **или** не читает рабочие
выгрузки пользователя.

**Вариант B (без Unica):** facade + r02 + скрипты r12 + r10 + r09.
Выигрыш: нативный Cursor, не зависит от 8.3.27 Unica.
Проигрыш: нет единого типизированного apply/view; больше склейки.

**Вариант C (EDT-only):** r17 + r09. Отклонён: ломает обязательные обычные
формы и выгрузки конфигуратора.

Гипотеза «explore/docs/edit/verify/debug как внешние имена» годится как
внутренняя нарезка facade. Debug отдельным продуктом не найден (кроме
r17 в EDT).

## Риски и ревью

Наиболее существенные неизвестные:

1. Подключение и поведение Unica в Cursor.
2. Точность `find_callers_context` / индекса r15 (хелперы r02 не
   трассировались построчно).
3. Обычные формы: Form.bin может сделать C3/C5 неудовлетворимыми без
   нового компонента.
4. Лицензии: Unica LGPL-3.0-or-later, METR GPL-3.0 — влияют на то, можно
   ли «вшивать» их в закрытый помощник. Как отдельные процессы MCP риск
   ниже, но это не юридическое заключение.
5. r04 не соберётся без соседнего checkout.
6. r07 README — шаблон; сам action существует в `src/index.ts`.

Режим ревью: самопроверка. Контрпример к варианту A (Unica недоступна /
обычные формы доминируют) не отменяет r02+r09; он переключает edit на
вариант B и оставляет пробел ОФ открытым. Вывод «не подключать все 19»
контрпримером не опрокинут.

Механический `kit.py check-run evaluations/main` — PASS (структура и
ссылки). Это не доказывает содержательную верность.
