## Вход пользователя

Собрать из существующих open-source компонентов максимально эффективный
AI-инструментарий для программиста 1С:Предприятие 8, пригодный для реальной
ежедневной разработки как с управляемыми, так и с обычными формами. Нужен не
набор из десятков одновременно подключённых MCP/skills и не монолит, а
минимальный и хорошо спроектированный контур, позволяющий coding-agent'у:
исследовать большие существующие конфигурации 1С без загрузки значительной
части конфигурации в контекст; находить BSL-код, определения, использования,
callers/callees, обработчики событий, подписки, работу с регистрами и другие
связи; понимать метаданные, управляемые и обычные формы и связанные с ними
модули; по необходимости получать точную справку по языку BSL и API платформы
1С; вносить изменения в BSL, формы, метаданные и другие исходники там, где это
технически возможно; выполнять статическую проверку изменений; обновлять/
собирать конфигурацию и запускать 1С; выполнять целевую runtime/UI/
автоматизированную проверку сделанных изменений; возвращать агенту компактные
структурированные результаты и evidence вместо больших логов, исходников и
сотен результатов поиска. Ключевой критерий — эффективность контекста: агент
не должен постоянно видеть десятки или сотни похожих tools, полную документацию
всех компонентов или большие результаты поиска. Нужно исследовать архитектуру
с небольшой стабильной внешней поверхностью для агента и более богатым
внутренним набором возможностей.

Машинная запись: [request.json](request.json).

## Результат и сценарии

Желаемый наблюдаемый результат: обоснованный минимальный набор существующих
компонентов (и, если нужно, тонкий собственный слой поверх них), из которого
можно собрать ежедневный контур агента для разработки 1С 8. Не набор из
десятков MCP/skills и не монолит «делает всё сам».

Пользовательские сценарии (из входа):

1. Агент исследует большую незнакомую конфигурацию и находит нужные объекты и
   связи, не загружая конфигурацию в контекст.
2. Агент находит определение и использования процедуры/функции BSL, обработчики
   событий, подписки и обращения к регистрам.
3. Агент получает точную справку по синтаксису BSL и API платформы по
   конкретному вопросу.
4. Агент вносит изменение в модуль формы (управляемой и обычной), метаданные
   или общий модуль.
5. Агент выполняет статическую проверку изменений и получает компактный список
   замечаний.
6. Агент обновляет/собирает конфигурацию, запускает 1С и выполняет целевую
   runtime/UI-проверку.
7. Агент получает компактный структурированный результат проверки и исправляет
   ошибку в цикле.

Текущее состояние: ничего не реализовано; есть только список кандидатов и
требования к архитектуре. Избегать разработки с нуля: индекс/парсер BSL и
метаданных, база справки платформы, движок статического анализа BSL, движок
сборки/запуска 1С, движок UI/функционального тестирования.

## Критерии

Категории выведены из цели: исследование исходников, справка, изменение,
проверка, эффективность контекста, независимость от адаптера, цикл обратной
связи. Деление explore/docs/edit/verify/debug — рабочая гипотеза, не
обязательная архитектура.

### C1 — Исследование больших конфигураций без загрузки в контекст

Обязательное. Успех: поиск сначала сужает пространство кандидатов и возвращает
краткие структурированные результаты, а не десятки файлов или полный исходный
код. Эталон: сценарий 1 и свойства progressive narrowing / search-then-read.
Вопрос: есть ли индекс/сервис вне окна контекста и отдельный шаг read фрагмента?

### C2 — Навигация по связям BSL

Обязательное. Успех: находятся определения, использования, callers/callees,
обработчики событий, подписки, обращения к регистрам и сопоставимые связи.
Эталон: сценарий 2. Вопрос: какие именно виды связей реализованы в коде, а не
только заявлены?

### C3 — Метаданные и оба типа форм

Обязательное. Успех: инструмент понимает метаданные, управляемые формы, обычные
формы и связанные модули. Поддержка «1С вообще», только EDT или только
управляемого приложения не считается доказательством обоих типов форм.
Эталон: явное требование пользователя. Вопрос: какой формат выгрузки и какие
типы форм реально разобраны?

### C4 — Точная справка по BSL и API платформы

Обязательное, по запросу. Успех: агент получает ответ по конкретному языковому
или платформенному вопросу без загрузки всей документации в контекст.
Эталон: сценарий 3. Вопрос: источник данных (HBK, дамп, ручной корпус), полнота
и возможность точечного чтения.

### C5 — Изменение исходников 1С

Обязательное. Успех: можно вносить изменения в BSL, формы, метаданные и другие
исходники там, где это технически возможно. Эталон: сценарий 4.
Вопрос: есть ли специализированные операции edit или только общий файловый I/O?

### C6 — Статическая проверка изменений

Обязательное. Успех: после правки доступна статическая проверка с компактным
списком замечаний. Эталон: сценарий 5.
Вопрос: какой движок (встроенный, bsl-language-server, EDT, иное) и какой вывод?

### C7 — Обновление, сборка и запуск 1С

Обязательное. Успех: конфигурацию можно обновить/собрать и запустить 1С из
контура агента. Эталон: сценарий 6, первая половина.
Вопрос: designer, ibcmd, EDT, OneScript, GitHub Action — что реально вызывается?

### C8 — Целевая runtime / UI / автоматизированная проверка

Обязательное. Успех: сделанные изменения проверяются точечно (тест, UI-сценарий,
вызов в ИБ), а не только «конфигурация открылась». Эталон: сценарий 6–7.
Вопрос: YaXUnit, Vanessa, RAT, UI-компоненты, HTTP/OData — что закрывает обычные
формы, что только управляемые?

### C9 — Компактные структурированные результаты

Обязательное. Успех: большие выдачи имеют фильтрацию, группировку,
pagination/narrowing или чтение выбранного фрагмента; агенту возвращается
evidence, а не сырые логи. Эталон: ключевой критерий эффективности контекста.
Вопрос: есть ли лимиты, страницы, выбор полей, запись артефакта во внешнее хранилище?

### C10 — Минимальная внешняя поверхность и progressive disclosure

Обязательное. Успех: агент постоянно видит небольшую стабильную поверхность;
подробные инструкции, документация и специализированные инструменты
подключаются только когда нужны. Эталон: архитектурные свойства 1 и 4.
Вопрос: facade/capability, lazy skills, один бинарник с скрытыми helper-ами?

### C11 — Знания вне окна контекста

Предпочтение. Успех: индексы, документация, результаты анализа и промежуточные
артефакты живут в файлах/БД/сервисе и возвращаются по запросу.
Эталон: архитектурное свойство 6.

### C12 — Независимость 1С-логики от способа подключения агента

Предпочтение. Успех: реальная работа с 1С отделена от MCP/CLI/Cursor/других
адаптеров; одна capability не реализуется несколько раз.
Эталон: архитектурное свойство 8.

### C13 — Замкнутый feedback loop

Обязательное как свойство контура, не одного репозитория. Успех: исследование →
изменение → статическая проверка → обновление/запуск → целевая проверка →
компактный результат → исправление. Эталон: архитектурное свойство 9 и сценарий 7.

### C14 — Отсутствие ненужного дублирования

Предпочтение для итоговой архитектуры. Успех: если два инструмента закрывают
одну capability, выбран основной, fallback/specialized либо исключение.
Эталон: архитектурное свойство 5. Не требует, чтобы каждый кандидат был уникален.

## Решения, ограничения и предположения

Решения пользователя:

- не писать с нуля то, что уже качественно реализовано;
- внешняя tool surface должна быть минимальной и стабильной;
- поддержка обычных форм обязательна наравне с управляемыми;
- на этом этапе только анализ: помощник не реализуется, инструменты не
  устанавливаются;
- упоминания Codex в методике трактовать как роль агента-исполнителя; комплект
  repo-evaluation-kit под Cursor не переделывать;
- не стремиться включить все 19 репозиториев.

Ограничения: Windows 10/11; Cursor Agent; open-source и сопровождение;
существующие большие конфигурации, не только новые проекты; на обзоре только
чтение публичных материалов.

Нежелательные зависимости: собственный парсер/индекс BSL, собственная база
справки, собственный анализатор, собственный движок сборки/запуска и UI-тестов.

Неизвестно: конкретные рабочие конфигурации пользователя, наличие EDT,
лицензии платформы, предпочтительный формат выгрузки (XML конфигуратора /
EDT), готовность ставить расширения в ИБ.

Предположения исследователя:

- A1: целевые исходники доступны как файловая выгрузка (XML конфигуратора
  и/или EDT). Влияет на пригодность кандидатов, завязанных на один формат.
- A2: агент исполняется в Cursor и может вызывать MCP, CLI и skills. Влияет
  на оценку адаптеров, но не должно определять ядро 1С-логики (C12).
- A3: деление explore/docs/edit/verify/debug — удобная рамка сравнения, не
  обязательный внешний API. Итоговая поверхность выводится из найденных
  возможностей.
- A4: «использовать как библиотеку/core» допустимо, даже если исходный
  MCP-интерфейс кандидата слишком широкий или дублирует другой.

## Объём и разрешения

Кандидаты: 19 входных URL, реестр [INVENTORY.json](INVENTORY.json).
Глубина: overview — первичный статический обзор всех входов. Для каждого
существенного заявления ищется относящийся код либо честно фиксируется
непросмотренное. Запуск кода, установка и клонирование исходников не
разрешены (`permissions.* = false`). Чтение публичных файлов через GitHub
API/веб входит в статический обзор.

Обещанные результаты этапа: BRIEF, заполненные карточки всех 19, матрица
по capability (не 19 независимых обзоров как главный вывод), REPORT с
рекомендацией минимального контура, VALIDATION с следующим экспериментом,
STATE для продолжения. После каждой карточки STATE обновляется.

Критерий закрытия этапа: все входы учтены, у каждого есть карточка,
выводы снабжены основаниями DOCUMENTATION/SOURCE/INFERENCE/UNKNOWN,
синтез и самопроверка выполнены, открытые проверки видимы. Это не готовность
внедрения и не deep-static/execution.

Оставшиеся вопросы к пользователю на этом этапе не блокируют обзор.
Нужны будут на этапе внедрения: формат рабочих конфигураций, наличие EDT,
допустимость расширения в ИБ, предпочтительный адаптер (MCP vs CLI vs skill).
