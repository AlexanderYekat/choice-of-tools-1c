# Проверки и следующий эксперимент

До исполнения все сценарии NOT_RUN. Основания: [EVIDENCE.json](EVIDENCE.json).

## Общий проверочный корпус

Для сравнимых explore-кандидатов (r02, r15, частично r01/r19) эталон один:

- Вход: одна и та же файловая выгрузка конфигурации с **хотя бы одной
  обычной формой** (FormType=Ordinary и/или Form.bin) и одной управляемой.
- Ожидание: найти объект, модуль формы, обработчики (если есть в XML),
  2–3 callers экспортного метода, не вернуть полные файлы.
- Метрика: число tools в `tools/list`; размер ответа в символах; полнота
  (нашлись ли definition/usages); отдельно — нашлась ли *структура* ОФ.
- Отрицательный контроль: запрос несуществующего символа → пусто/not_found,
  не простыня файлов.
- Пограничный: модуль на 2000+ строк — должен вернуться фрагмент/сигнатуры.

Для docs (r04/r10/unica.docs): один запрос `СтрНайти` / `HTTPСоединение`.
Для verify (r09): один модуль YaXUnit, эталон — компактный список падений.

Авторские бенчмарки r02/r15 в корпус не входят.

## Следующий ограниченный эксперимент

Вопрос/гипотеза: **Вариант A жизнеспособен, если в Cursor поднимается
Unica и `unica.view` на адресе обычной формы не является слепым отказом
без альтернативы; иначе edit-контур сразу планировать как вариант B, а
пробел структуры ОФ считать открытым независимо от хоста.**

Выбранные версии: r01 `56a67d4a460c97101b6b542b4fe940298ab0edd8`.

Вход и эталон: локальная выгрузка конфигуратора с одной УФ и одной ОФ;
ожидаемые имена tools из `EXPECTED_COMPATIBILITY_TOOLS`; для УФ —
проекция элементов; для ОФ — честно зафиксировать, что именно вернулось
(проекция / только метаданные / ошибка).

Среда и разрешения: Windows, Cursor, установка Unica runtime (потребуется
явное разрешение `install_dependencies`/`start_services` и сеть на
релизы unica-toolchain). Платформа 8.3.27 желательна, иначе сразу
зафиксировать отказ версии.

Шаги (исполнять только после разрешения):

1. Подключить бинарь `unica` как stdio MCP в Cursor (не обязательно
   marketplace Codex).
2. Вызвать `tools/list`, сравнить с 11 именами.
3. `unica.view {}` на workspace.
4. Найти обе формы через `unica.search {corpus:"names"}`.
5. `unica.view` на каждой.
6. Остановить: не вызывать `apply` с `dryRun:false`.

Наблюдаемый PASS: 11 tools; УФ даёт структуру; ОФ либо читается, либо
ошибка с явным кодом (не молчаливая подмена УФ).
Наблюдаемый FAIL: сервер не стартует; tools/list другой; зависание
bootstrap.
Отрицательный контроль: `unica.view` на несуществующем `at` → not_found.

Ограничение: один вечер, одна выгрузка, без правки файлов. Стоп, если
bootstrap не завершился за 15 минут.

Решение после исходов:

- PASS + ОФ читается хоть как метаданные → оставить вариант A, запланировать
  отдельный эксперимент структуры Form.bin.
- PASS + ОФ слепой отказ → A для УФ/метаданных, C3 открыт, не обещать ОФ.
- FAIL подключения → вариант B (r02+r12+r10+r09), Unica отложить.

Исполнитель: следующий CONTINUE-AUDIT с разрешениями. Артефакт: лог в
`evaluations/main/sources/` и обновление карточки r01 / REPORT.

Этот эксперимент предложен и **не запускается** этим заданием.
