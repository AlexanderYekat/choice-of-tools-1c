# План реализации фасада с чекпоинтами

Дата: 2026-09-22. Версия цели: 2. Источник —
[FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md) (техника) и
[FACADE-TZ.md](FACADE-TZ.md) (методология, включая §2a — v8-harness как
основа ConfigLoader/TargetRegistry для слоя r22/Vanessa).

**Статус документа:** план работы, не код и не его начало. Запрет
писать код фасада **не снят** этим документом — см. CP0. Чекпоинты
режут [FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md) на последовательные
куски работы; каждый — с объёмом, зависимостями и проверяемым критерием
приёмки. Ничего из плана не исполняется автоматически.

## Как читать

- Чекпоинты идут по возрастанию риска и зависимостей: сначала
  фундамент (конфиг, envelope), потом самый простой адаптер, потом
  самые сложные (Unica — асинхронность и publish, r22 — интеграция с
  v8-harness и честная обработка E1), потом остальное.
- Каждый чекпоинт закрывается **проверяемо**: конкретный вызов через
  реальный фасад на стенде `simple`, сверяемый с уже существующими
  логами static-стыковки — не «код написан», а «код даёт тот же
  результат, что и прямой вызов продукта».
- Неполный фасад — не провал. Принцип 3 [FACADE-TZ.md](FACADE-TZ.md)
  §11: «нет Vanessa — живут поиск и правки». Если реализация
  остановится после CP6, это рабочий частичный фасад, а не брак.
- Каждый чекпоинт указывает: **Опирается на** (разделы техТЗ), **Входит
  / Не входит**, **Критерий приёмки**, **Риски и открытые решения**.

## CP0 — Разрешение и нерешённые вопросы стека

**Опирается на:** [FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md) §0.

**Входит:**
- Явное разрешение пользователя писать код фасада (снимает запрет из
  [INTEGRATION-PLAN.md](INTEGRATION-PLAN.md)/[STATE.md](STATE.md)).
- Подтверждение или смена трёх дефолтов §0: рантайм (Python 3.11+),
  форма поставки (stdio MCP сервер), место кода (вне
  `evaluations/main`).
- Выбор конкретного каталога/репозитория для кода.

**Не входит:** сам код, даже каркас.

**Критерий приёмки:** есть явное «да, пиши код» + подтверждённые/
изменённые три дефолта, зафиксированные в `STATE.md`. Без этого CP1 не
начинается.

**Риски:** ни один — это организационный гейт, не техническая работа.

## CP1 — ConfigLoader + TargetRegistry + ProjectDetector

**Опирается на:** [FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md) §2
(компоненты), §3 (конфигурация).

**Входит:**
- `ProjectDetector`: единственная проверка — есть ли `v8stands.yaml` в
  корне. Нет файла → 1С-операции не регистрируются, никакой эвристики
  по `Configuration.xml`/`.mdo`.
- `ConfigLoader`: вызывает `v8_harness.load_stands(root)` (импорт как
  библиотеки — рантайм совпадает, см. §0) либо `status`/`sync` через
  subprocess, если импорт неудобен. Не пишет свой YAML-парсер.
- Чтение двух новых опциональных полей на стенде: `read_source`,
  `role`. Игнорирование отсутствия — `read_source` = `sources`,
  `role` = не задана (verify тогда должен трактовать как «не test/dev»,
  см. CP5/CP6/CP7 — не по умолчанию разрешать).
- `TargetRegistry`: резолвит имя `target` → запись стенда;
  `target_not_found`/`target_ambiguous` по таксономии §5.

**Не входит:** сам вызов какого-либо продукта (r01/r15/r20/r22),
envelope, ArtifactStore — это ещё заглушки/не существуют.

**Критерий приёмки:** на стенде `simple`
(`.v8/stands/simple/v8project.yaml` уже сгенерирован v8-harness)
`TargetRegistry.resolve("simple")` отдаёт корректные `sources`,
`read_source` (если задан), `role`, путь к сгенерированному
`v8project.yaml` — без вызова r01/r15/r20/r22. Несуществующее имя цели
→ `target_not_found` с тем же текстом, что даёт `v8_harness.
runner_command` (§5 техТЗ, строка `target_not_found`).

**Риски:** если импорт `v8_harness.py` как модуля неудобен
(например из-за пути установки), fallback — вызывать `status`/`sync`
subprocess'ом и парсить их JSON `print_report`; сам facade всё равно не
пишет YAML-парсер заново.

## CP2 — Envelope, таксономия ошибок, ArtifactStore, пустой Router

**Опирается на:** [FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md) §4
(envelope), §5 (таксономия), §6 (порог инлайна).

**Входит:**
- `EnvelopeNormalizer`: единая форма ответа
  `{ok, operation, target, data, artifacts[], diagnostics[],
  duration_ms}`.
- `ArtifactStore`: порог 8192 байт, имя файла
  `.v8/artifacts/<operation>-<target>-<unix_ms>.<ext>`, запись в
  `.gitignore`.
- `Router`: принимает 7 имён операций, для каждой пока — заглушка
  (`NotImplementedError`/фиксированный `ok=false` с `code:
  "not_implemented"` — новый служебный код, не из таксономии продукта),
  чтобы можно было протестировать форму ответа до появления реальных
  адаптеров.
- Таксономия ошибок §5 реализована как набор именованных констант/типов,
  без привязки к конкретному адаптеру.

**Не входит:** реальные вызовы продуктов.

**Критерий приёмки:** unit-тест (не прогон на стенде) — `ArtifactStore`
пишет файл и возвращает путь ровно при превышении 8192 байт, не раньше;
`docs`/`verify.form.screenshot` уходят в файл безусловно даже при
малом размере (тестовые фикстуры с искусственно маленьким payload).
`EnvelopeNormalizer` даёт одинаковую форму для трёх раздельно
сконструированных «сырых» ответов (имитация Unica/`r22`/Answer42).

**Риски:** порог 8192 — предположение техТЗ, не проверенный прогоном
факт (см. трассируемость [FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md)
§12). Если на реальных данных порог окажется неудобным — править
точечно здесь, не открывать заново весь бюджет контекста.

## CP3 — IndexAdapter (`explore`)

**Опирается на:** [FACADE-TZ.md](FACADE-TZ.md) §5.1, таблица S1–S5
([VALIDATION.md](VALIDATION.md)).

Выбран первым среди пяти адаптеров: самый простой контракт — read-only,
CLI без демона обязателен (`bsl-indexer search-function`), нет
async/dual-session сложностей.

**Входит:**
- `explore(source, query)` → вызывает `r15` CLI ядра (`search-function`/
  `get-callers`/аналоги) на `stand.read_source` (или `sources`, если
  `read_source` не задан).
- Проброс через `EnvelopeNormalizer`/`ArtifactStore` из CP2.

**Не входит:** MCP-режим `r15` (демон + `[tools].enabled``) — CLI
ядра достаточно для `explore`; MCP-путь — опциональное расширение
позже, если понадобится живой индекс без перезапуска.

**Критерий приёмки:** `explore("simple", "РассчитатьСумму")` через
фасад даёт envelope с `data`, сопоставимый по содержанию с сырым
`search-function РассчитатьСумму` из
[logs/e3-chain-simple.md](logs/e3-chain-simple.md) (шаг 1, 3202 байта) —
инлайн, без артефакта (ниже порога §6).

**Риски:** минимальны — самый безопасный первый шаг, продукт уже
CLI-first (`S1: удобно` в [VALIDATION.md](VALIDATION.md)).

## CP4 — UnicaAdapter (`docs`, `edit.view`, `edit.apply`, `static.unica`)

**Опирается на:** [FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md) §7.1
(формат 2.20/1.0), §7.6 (асинхронность `docs`), §9 (жизненный цикл
процессов, строка r01).

Самый сложный из пяти адаптеров: долгоживущий демон, асинхронная
задача, dryRun/`ifRev`-протокол для записи.

**Входит:**
- `ProcessManager` держит один stdio-демон Unica на процесс фасада,
  один `UNICA_PROVIDER_STATE_DIR` (обязательное условие §7.6).
- `docs(source, query)`: вызывает `unica.docs`, сам поллит
  `unica.task.result` (бэкофф от 200 мс, таймаут по умолчанию 60 с),
  агенту — уже готовый envelope, без промежуточных `status`.
  `77 205` байт → безусловно в артефакт (не по порогу, по правилу §6).
- `edit.view(target, at)`: `unica.view`, `sources`/`read_source` по
  §7.1.
- `edit.apply(target, at, ops, dryRun, ifRev?)`: `dryRun` по умолчанию
  `true`; `dryRun:false` без предшествующего `dryRun:true` в этой же
  сессии → `missing_ifrev` (фасадная проверка, не пропускать сразу в
  Unica); `stale_revision` — проброс как есть.
- `static.unica(target, at?)`: `unica.check`.
- Обработка `invalid_source`/`source_unreadable` → `source_format_
  unwritable` с сообщением про `read_source` (§7.1).

**Не входит:** `static.syntax` (r22-часть, CP5); build (CP5).

**Критерий приёмки:** воспроизвести через фасад на стенде `simple`/
`cf220`-эквиваленте (`read_source`/`sources` стенда) результаты,
сопоставимые с [logs/r01-mcp-apply-cf220-simple.md](logs/r01-mcp-apply-cf220-simple.md)
и [logs/r01-mcp-apply-publish-simple.md](logs/r01-mcp-apply-publish-simple.md):
dryRun preview + `rev`, публикация с `ifRev` → `mode=published`,
повторный `ifRev` → `stale_revision`. `docs` на запрос «НаборЗаписей» —
артефакт в файл, summary + путь в envelope, числа сходятся с
[logs/e3-chain-simple.md](logs/e3-chain-simple.md) (77 205 байт / 800
строк / 80 hits).

**Риски:** если фасадная проверка `missing_ifrev` окажется избыточной
(Unica и так отказывает без `ifRev`) — упростить до простого
проброса, не держать дублирующую проверку ради проверки.

## CP5 — RunnerAdapter (`build`, `static.syntax`, `verify.unit`) через v8-harness

**Опирается на:** [FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md) §7.2
(владелец ИБ), §7.3 (владелец рабочего дампа), §7.4 (имя расширения),
§7.5 (`--sources` YaXUnit), §7.7 (incremental build), §8 (честная
реализация E1), §9 (строка r22).

**Входит:**
- Все вызовы `r22` идут через `v8-harness run --stand <target> -- …`
  (subprocess) или `v8_harness.runner_command(root, target, extra)`
  (импорт) — фасад не собирает `--config` сам (прямое следствие CP1 +
  §2a методТЗ).
- `build()` — внутренний шаг, не внешняя операция: partial → на отказе
  «файл-список загружаемых файлов» одна автоматическая повторная
  попытка `--full-rebuild` (§7.7), не более одной.
- `static.syntax(target)`: `syntax designer-modules --server
  --thin-client`.
- `verify.unit(target, module?)`: гоняет build (с fallback) +
  `test yaxunit`; при «0 сценариев + активное расширение» — envelope
  `ok=false`, `code: verify_unavailable`, **без** попытки скрыть отказ
  или подменить его `verify.form`/`verify.scenario` (§8, дефолт
  [FACADE-TZ.md](FACADE-TZ.md) §14 п.5).
- Best-effort сверка имени расширения перед `verify.unit` (§7.4),
  `--sources`/`DESIGNER` правило по `from: cf` (§7.5).
- Роутер объединяет `static.unica` (CP4) + `static.syntax` в единый
  ответ операции `static`.

**Не входит:** изоляция причины E1 самой по себе — не задача фасада
(дефолт [FACADE-TZ.md](FACADE-TZ.md) §14 п.5); фасад обязан только
честно её отражать.

**Критерий приёмки:** на стенде `simple` через фасад — `static.syntax`
даёт `status=clean`, сопоставимо с
[logs/r22-syntax-modules-simple.json](logs/r22-syntax-modules-simple.json);
`verify.unit` даёт `ok=false`/`verify_unavailable` — **обязательный
регрессионный тест**: если реализация вдруг вернёт `ok=true` без
предварительно задокументированного закрытия E1, это баг фасада
(ложноположительный тест зелёного), не повод праздновать.

**Риски:** это самый рискованный чекпоинт наравне с CP4 — зависит от
устойчивости интеграции с v8-harness (импорт vs subprocess) и от того,
не появится ли к моменту реализации решение по E1 (тогда шаг 2 из §8
техТЗ меняется на обычный pass/fail без специальной обработки — не
регресс, а ожидаемое обновление).

## CP6 — FormAdapter (`verify.form`)

**Опирается на:** [FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md) §9
(строка r20).

**Входит:**
- Долгоживущая stdio-сессия Answer42, `session_id = target`.
- Идемпотентность: повторный `verify.form` на той же цели переиспользует
  сессию, не поднимает третий клиент.
- `screenshot` — безусловно в артефакт (PNG путь, не base64 — уже
  корректно у продукта, фасад просто пробрасывает путь).
- `start_session` (9960 байт) пересекает порог §6 — автоматически в
  файл, без отдельного правила.

**Не входит:** RAG-профиль Answer42 как explore (не подменять
`IndexAdapter`, принцип из раздела 3 методТЗ).

**Критерий приёмки:** воспроизвести через фасад
`start_session`→`active_window`→`screenshot`→`stop_session`,
сопоставимо с [logs/r20-mcp-simple.md](logs/r20-mcp-simple.md).

**Риски:** минимальны, продукт уже даёт узкий `--tool-profile ui
--disable-rag` (103 из 122 статических tools), фасад дополнительно не
сужает набор функций Answer42, только маршрутизирует вызовы.

## CP7 — ScenarioAdapter (`verify.scenario`)

**Опирается на:** [FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md) §9
(строка r21) — тривиальное расширение CP5, не отдельный процесс.

**Входит:**
- `verify.scenario(target, feature, peer?)` → `RunnerAdapter` вызывает
  `test va` тем же путём, что и остальной `r22` (через v8-harness).
- `peer` — заложить параметр в сигнатуру уже сейчас (раздел 7
  методТЗ), даже если одновременность двух Test Client Vanessa
  остаётся UNKNOWN осознанно — не реализовывать одновременный запуск
  без отдельной проверки.

**Не входит:** MCP Vanessa (интерактивная отладка, не основной путь).

**Критерий приёмки:** через фасад — `smoke-engine.feature`, 1/1 PASS,
сопоставимо с [logs/r22-va-smoke-simple.md](logs/r22-va-smoke-simple.md).

**Риски:** нет отдельных — весь риск уже покрыт CP5 (эта операция —
тонкая обёртка над уже сделанной интеграцией).

## CP8 — Два target одновременно

**Опирается на:** [FACADE-TZ.md](FACADE-TZ.md) раздел 4 и раздел 9
(стыки), [logs/r01-r22-e2-two-targets.md](logs/r01-r22-e2-two-targets.md).

**Входит:**
- Второй стенд в `v8stands.yaml` (например копия `ib-b`, уже созданная
  ранее в `.v8/work/r20-dual/`, переиспользуется — не плодить новую
  ИБ).
- Через фасад — операция на цели A не меняет sha256 ИБ цели B
  (воспроизвести проверку E2b), несуществующий `target` — явный
  `target_not_found`, без отката на дефолтную цель.
- Для Unica — если пути обоих стендов под общим корнем workspace,
  адресация через `at="<source-set>:…"` в одном сгенерированном
  `v8project.yaml`; если нет общего корня — второй процесс/cwd
  (ограничение уже зафиксировано в [FACADE-TZ.md](FACADE-TZ.md) §4).

**Не входит:** одновременность двух активных Vanessa Test Client —
остаётся UNKNOWN осознанно, не проверяется здесь.

**Критерий приёмки:** та же проверка, что в E2, но выполненная **через
фасад**, не прямыми вызовами продукта — sha256 обеих ИБ до/после,
именованный отказ на несуществующей цели.

**Риски:** Unica requires workspace-relative пути без выхода за корень
(обнаруженное ограничение E2a) — если у реальных двух целей нет общего
предка, придётся либо мириться с двумя процессами Unica, либо это
фиксируется как известное ограничение фасада, не решается изобретением
обхода.

## CP9 — Бюджет контекста на полном цикле

**Опирается на:** [FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md) §6,
[FACADE-TZ.md](FACADE-TZ.md) раздел 8.

**Входит:**
- Один сквозной цикл через фасад: `explore → docs → edit.view/apply
  dryRun → static → verify.unit → verify.form → verify.scenario`,
  вызовами агента через уже собранный Router (CP2–CP7), не прямыми
  вызовами продуктов.
- Замер суммарного объёма, ушедшего в чат (не в артефакты).

**Не входит:** оптимизация продуктов — если конкретный шаг регулярно
превышает порог, чинится порог/пост-обрезка в `ArtifactStore` (CP2),
не сам продукт.

**Критерий приёмки:** сумма в чат укладывается в ≈30 КБ, как
предсказано в [logs/e3-chain-simple.md](logs/e3-chain-simple.md). Если
превышает — это регресс §6, фиксируется как открытая проблема CP10,
не тихо игнорируется.

**Риски:** первый реальный сквозной прогон через код (не через
отдельные `run-*` скрипты) — здесь наиболее вероятны неучтённые мелочи
интеграции между чекпоинтами (например порядок вызовов, состояние
`ProcessManager` между операциями).

- Сверка критериев приёмки [FACADE-TZ.md](FACADE-TZ.md) §13 (таблица

  `VERIFIED_INTEGRATION` по факту прогона через код, какие остаются
  открытыми.
- Явное решение пользователя: считать фасад v0 готовым к использованию
  на стенде `simple`, продолжать ли на реальном проекте, возвращаться
  ли к изоляции причины E1.

**Не входит:** публикация/дистрибуция фасада как отдельного продукта
(упаковка, документация для сторонних пользователей) — отдельная
задача после решения по итогам этого чекпоинта, не часть v0.

**Критерий приёмки:** каждый из 9 пунктов §10 либо PASS со ссылкой на
факт прогона, либо честно зафиксирован как FAIL/открытый риск —
как это уже сделано для E1 на всех предыдущих этапах этого запуска, не
переоценивается в сторону PASS без основания.

**Риски:** нет технических — это точка решения, не работы.

## Что этот план не делает

- Не назначает сроки/оценки трудозатрат — вне методики этого запуска.
- Не выбирает между CP0 (реализация по чекпоинтам целиком) и частичной
  реализацией (например только CP1–CP4, без verify-слоёв) — это выбор
  пользователя в момент CP0.
- Не отменяет и не пересматривает ни один факт/дефолт
  [FACADE-TZ.md](FACADE-TZ.md)/[FACADE-TECH-SPEC.md](FACADE-TECH-SPEC.md)
  — только режет техническое ТЗ на последовательные куски работы.
