# Методика фасада

Дата: 2026-09-20. Статус: черновик договорённости, не код и не жёсткий контракт.

Состав продуктов: [DECISION.md](DECISION.md). Этот файл — как устроена
**обвязка** и чего мягко ждать от пяти инструментов, чтобы потом проверить
стыковку. Если инструмент не ляжет в фасад как есть — сначала крутим фасад,
и только если не выходит — правим код того продукта.

Имена операций ниже — смысл, не обязательный API.

## Зачем фасад

Агент должен видеть **мало стабильных действий**: найти, прочитать справку,
посмотреть/поменять исходник, статически проверить, прогнать проверку.
Внутри — Unica, code-index-mcp, mcp-onec-test-runner, Answer42, Vanessa.

Без фасада в `tools/list` снова окажутся десятки операций пяти MCP.
Фасад не пишет парсер BSL, индекс, справку платформы, сборку 1С и UI-тесты.

## Принципы (гибкие)

1. **Включение по проекту, не глобально.** Не каждый репозиторий — 1С.
   В обычном TypeScript/Python-проекте контур 1С не показывается.
2. **Один проект — несколько целей.** Выгрузка, информационная база,
   сторона обмена — именованные сущности, а не «единственная база навсегда».
3. **Неполный набор допустим.** Нет Vanessa — живут поиск и правки.
   Нет живой 1С — нет form/scenario, остальное работает.
4. **Большое на диск, в чат — коротко.** Поиск, дерево формы, лог теста
   не должны заливать контекст.
5. **Сначала адаптер, потом чужой репозиторий.** Форк пяти продуктов —
   запасной путь, не первый.
6. **Хост агента не диктует ядро.** Codex, Claude, Cursor или CLI —
   разные адаптеры к одним и тем же операциям.
7. **Разрушительное — явно.** Запись в исходники, загрузка в ИБ, проведение
   документов, прогон на «не тестовой» базе — с именем цели и без молчаливого
   дефолта на прод.

Это предпочтения. Если продукт умеет иначе, фасад может обернуть.

## Когда фасад молчит

Контур 1С **включается только если проект сам об этом сказал**.

Признаки включения (достаточно одного, точный формат выберем при реализации):

- в корне есть манифест вроде `.1c-agent.yaml` / `v8project.yaml`;
- или каталог выгрузки конфигурации явно указан в этом манифесте;
- или пользователь в этом чате сказал «это 1С-проект».

Нет признака — фасад не регистрирует 1С-операции. Глобально ставить
пять MCP «на всю машину» не нужно: иначе агент в чужом репозитории
будет искать `Справочник.Номенклатура`.

В одном воркспейсе с несколькими корнями: 1С-операции только у корня
с манифестом. Соседний сервис на Go фасада не видит.

## Контекст проекта

В манифесте проекта (черновик полей, не схема):

| Поле | Зачем |
|---|---|
| `enabled` | Вкл/выкл контура в этом репозитории |
| `sources[]` | Каталоги выгрузки (конфигуратор XML и/или EDT), в т.ч. несколько конфигураций |
| `targets[]` | Именованные информационные базы: `dev`, `test-sales`, `exchange-a` |
| `default_target` | Куда идут verify, если агент не уточнил |
| `capabilities` | Какие слои включены: explore / docs / edit / static / verify.* |
| `platform` | Версия платформы, если важна (например 8.3.27 под Unica) |

У **цели** (`target`): строка соединения или путь файловой ИБ, пользователь
для тестов (не в чат, а в локальный credentials-файл), роль (`dev` / `test` /
`never-prod`), сторона обмена (`a` / `b` / нет).

У **исходников**: путь, формат (`cf-xml` / `edt`), какая это конфигурация
(`main`, `extension`, `exchange-peer`).

Секреты в git и в аргументы MCP агенту не кладём.

## Несколько баз в одном проекте

Типовой случай — **обмен**: две информационные базы, иногда две выгрузки.

Агент всегда работает с **именем цели**, не с «текущей единственной 1С».

Примеры:

- `explore` по выгрузке стороны A, `verify.form` на базе `exchange-a`;
- поправить общий модуль в одной конфигурации, прогнать YaXUnit на `test`;
- сценарий Vanessa: провести документ в `exchange-a`, проверить появление
  в `exchange-b`.

Фасад не обязан сам реализовать протокол обмена. Он должен:

- не затирать «текущую базу» глобально, когда целей две;
- позволить указать `target` (и пару `target` / `peer`) на verify;
- не смешивать индексы двух выгрузок без явного `source`.

Если инструмент умеет только одну сессию 1С — это мягкий минус: фасад
держит две сессии снаружи или запускает инструмент дважды с разным
контекстом. Не обязательно, чтобы Vanessa из коробки знала «обмен».

## Что ещё заложено (не жёстко)

Имело смысл сразу иметь в виду, без превращения в анкету:

- **Тестовая vs любая другая база.** По умолчанию verify только на целях
  с ролью `test` / `dev`. Прод — отдельное явное разрешение.
- **Живая 1С не нужна для поиска и правок файлов.** Explore/edit/docs
  работают от выгрузки. Form/scenario — когда подняты Test Client и база.
- **Расширения.** Отдельный `source`, не обязательно вторая ИБ.
- **Подрезать контур.** В проекте обмена можно выключить Vanessa и оставить
  Answer42; в библиотеке общих модулей — только explore/edit/static.
- **Артефакты.** Отчёты тестов, деревья форм, фрагменты поиска — в каталог
  проекта (например `.1c-agent/artifacts/`), в чат ссылка и вывод.
- **Идемпотентность сессий.** Повторный `verify.form` на той же цели не
  обязан поднимать третий клиент 1С, если сессия уже есть.

## Внешняя поверхность

Ориентир: **около пяти–восьми операций**, не пять MCP целиком.

```
(только если проект 1С включён)

explore                 → code-index-mcp / bsl-indexer   (+ source)
docs                    → Unica
edit.view / edit.apply  → Unica                          (apply — явно)
static                  → Unica и/или синтаксис r09
verify.unit             → r09 + YaXUnit                  (+ target)
verify.form             → Answer42                       (+ target)
verify.scenario         → Vanessa                        (+ target, опционально peer)
```

Нет бэкенда или нет живой базы — операция отвечает «недоступно, почему»,
а не пропадает молча и не подменяет собой соседний слой
(Answer42 не становится поиском по коду).

## Мягкие требования к пяти инструментам

Не отборочный экзамен. Шкала для следующего исследования:

- **удобно** — фасад вызывает как есть (CLI, stdio, одна сессия, цель
  задаётся аргументом);
- **терпимо** — фасад оборачивает (фильтр tools, рабочий каталог, два
  процесса, пост-обрезка вывода);
- **мешает** — без правки продукта не стыкуется (только глобальный
  singleton базы, обязательно светить 30 tools, нет пакетного режима).

Общее, ко всем пяти:

| Предпочтение | Зачем |
|---|---|
| Можно звать не из «всего MCP сразу»: CLI, stdio, библиотека, узкий набор tools | Иначе фасад бесполезен |
| Есть куда передать путь выгрузки / имя ИБ / каталог проекта | Несколько целей и несколько проектов |
| Вывод можно ограничить или забрать файлом | Контекст |
| Старт без интерактива (флаги, конфиг, env) | Агент не заполняет GUI инструмента |
| Лицензия позволяет вызывать снаружи как процесс | Не обязательно влинковывать |

По слоям (всё «желательно», не «без этого выкидываем»):

**code-index-mcp / `bsl-indexer`**  
Индекс от каталога выгрузки; повторный индекс не с нуля; запрос
«найди / покажи фрагмент / callers» без полного файла; два корня
исходников — два индекса или явный `source`. Широкий `tools/list`
терпим, если фасад зовёт бинарь и не проксирует все tools.

**Unica**  
Чтение и правка по выгрузке; справка точечно; check узла; apply с
сухим прогоном или явным подтверждением. Не обязана быть поиском
по графу и UI-тестом. Хост Codex/Claude — нормально, фасад может
звать тот же stdio-бинарь.

**mcp-onec-test-runner**  
Сборка и YaXUnit на **указанной** ИБ; компактный отчёт одного модуля;
не требует, чтобы это была единственная база на машине.

**Answer42**  
Сессия Test Client на указанном `base_url` / цели; короткая проверка
формы; скрин или evidence в файл. RAG метаданных не использовать как
основной explore. Две базы обмена — две сессии или смена `target`.

**Vanessa**  
Запуск конкретного `.feature` / сценария; результат pass/fail по шагам
в компактном виде; привязка к базе (и при обмене — к паре баз, хотя бы
двумя запусками). Не обязана заменять Answer42 в коротком цикле.

## Порядок доработки

1. Фасад принимает чужой CLI/MCP как есть.
2. Не стыкуется — адаптер: рабочий каталог, обрезка JSON, выбор subset
   tools, два процесса, свои имена целей.
3. Совсем не стыкуется — точечный патч/форк **того** продукта, с записью
   зачем. Не переписывать продукт «под наш монолит».

Писать свой индекс, справку, сборку или UI-движок по-прежнему не цель.

## Следующий шаг исследования

Не новый каталог и не обзор всех 19. По каждому из пяти:

1. Чем его вообще звать (CLI / stdio MCP / HTTP / только GUI).
2. Как передать каталог выгрузки и/или информационную базу.
3. Можно ли не светить весь `tools/list` агенту.
4. Две цели в одном проекте: получается снаружи или мешает singleton.
5. Вывод: удобно / терпимо / мешает; что менять в фасаде; нужен ли патч.

Answer42 и Vanessa в обзоре 19 не разбирались — для стыковки их смотреть
наравне с Unica, r15 и r09.

Пока это не сделано, внедрять «все пять MCP в Cursor на всю машину»
не стоит: сломается и правило «не каждый проект — 1С», и узкая поверхность.
