## Главное уточнение: CLI у Vanessa уже есть

Vanessa исторически умеет **пакетный запуск из командной строки**.
Это не отдельный нативный `vanessa.exe`: запускается клиент 1С,
который открывает `vanessa-automation.epf` через `/Execute`, а
параметры передаются через `/C` и/или `VAParams.json`.

Документированный пример:

```text
1cv8c /TestManager
      /Execute "...\vanessa-automation.epf"
      /IBConnectionString "..."
      /C"StartFeaturePlayer;VAParams=C:\Temp\VAParams.json"
```

`StartFeaturePlayer` включает пакетное выполнение; основная форма
по умолчанию не показывается, а редактор не инициализируется, если
явно не передать `ShowMainForm` / `UseEditor`.

В репозитории есть и OneScript-обвязка `tools/onescript/RunVA.os`,
которая запускает процесс 1С, ждёт его завершения и читает файл статуса.

Следовательно, для нашего фасада **MCP не обязателен для
`verify.scenario`**. Есть два реальных пути интеграции:

1. batch CLI через 1С — хороший кандидат для обычного автономного прогона;
2. Streamable HTTP MCP — удобнее для интерактивной отладки уже поднятой
   Vanessa/Test Client с вызовами `run_scenario`, `get_test_results`
   и UI-инструментов.

## Batch CLI — самый короткий путь для facade

Для обычного автономного прогона предлагаемый контракт может быть:

```text
verify.scenario(target, feature, scenario?)
  -> facade формирует временный VAParams.json
  -> target -> строка подключения / Test Client profile data
  -> feature -> КаталогФич (может быть один .feature)
  -> scenario -> СписокСценариевДляВыполнения (если нужен)
  -> запускает 1cv8c /Execute vanessa-automation.epf /C StartFeaturePlayer...
  -> Vanessa пишет status file
  -> 0 = success, 1..4 = классифицированный failure
  -> расширенные логи/Allure/JUnit остаются artifacts
  -> агенту короткий структурированный итог
```

Документация прямо определяет status file:

- 0 — ошибок нет;
- 1 — ошибки сценариев;
- 2 — ошибка context/Test Client/network;
- 3 — сценарии не найдены;
- 4 — не установилась VanessaExt.

Это уже почти готовый **CLI adapter contract** без изменения Vanessa.

## MCP — второй, интерактивный путь

Документация показывает локальный Streamable HTTP MCP. В исходнике есть
`run_scenario(filePath, mode)`, `get_test_results`,
`manage_test_client(profileName)` и управление UI.

Статически найдено 40 tool descriptors. Три отключены
(`get_all_steps_in_json_format`, `get_current_date`,
`execute_step_from_text`), а регистратор пропускает disabled entries.
Итого **37 statically active MCP tools** на закреплённом SHA.

Для нашего coding-agent их показывать не надо. Если фасад выбирает MCP
для интерактивной сессии, он сам вызывает только нужный subset.

## Несколько ИБ

Документация CLI допускает передачу массива `ДанныеКлиентовТестирования`
с несколькими профилями и разными строками подключения. MCP также имеет
таблицу именованных profiles и подключение по `profileName`.

Однако статическое чтение не доказывает, что один процесс/MCP одновременно
держит две активные базы и выполняет единый exchange-сценарий. Поэтому
для S4 это остаётся UNKNOWN именно в части одновременности.

Если execution покажет ограничение на один текущий client, адаптер может
изолировать цели отдельными процессами/портами. Это пока гипотеза, не
найденная возможность Vanessa.

## Project detection

Vanessa знает `WorkspaceRoot` / `КаталогПроекта (projectpath)`, но
это явная настройка, а не доказанный generic detector любого 1С-проекта.
Многоагентные шаблоны Vanessa имеют свои `ТестПлан.MD` и
`ПараметрыКонфигурации.MD`, но они не должны становиться обязательным
манифестом нашего фасада.

## Резюме

r21 **сильнее стыкуется с фасадом, чем выглядело до углубления**.
Для обычного `verify.scenario` вероятно вообще не нужен MCP: у Vanessa
уже есть старый пакетный CLI-контур, одиночный feature-файл, фильтр
сценариев и машинный status file. MCP имеет смысл оставить как
интерактивный backend для разработки/отладки.

Следующая проверка после static-стыковки пяти — execution одного feature
через batch CLI; MCP и two-target exchange можно проверять отдельно.
