## Главное уточнение: CLI ядра есть, 1С-tools — MCP + демон

Точка входа контура — бинарь **`bsl-indexer`** (не публичный `code-index`
без XML-метаданных). Общая CLI-обёртка `code_index_core::cli::run`:

- one-shot: `index`, `search_function` / `get_function` / `get_callers` /
  `grep_body` и соседние — JSON в stdout из `<корень>/.code-index/index.db`;
- MCP: `serve --transport stdio|http` (stdio по умолчанию) — **только
  чтение**;
- индексатор: `daemon run` (или разовый `index`).

Именованных CLI-подкоманд для `get_object_structure`, `get_form_handlers`,
`get_event_subscriptions`, `get_register_writers` и прочих 1С-tools **нет**.
Следствие: выбранный слой C1/C2 для метаданных и handlers — MCP-клиент к
узкому subset, с живым демоном. Это **терпимо**, не «мешает»: пакетный
вход есть (CLI ядра + stdio MCP, без GUI продукта). Живая 1С на старте
не нужна.

Документация и заголовок MCP: без `daemon run` и общего `CODE_INDEX_HOME`
вызовы `serve` отвечают `daemon_offline`, даже если `index.db` уже есть.
One-shot CLI этот гейт обходит (открывает БД напрямую). npm-пакет
`@regsorm/code-index-mcp` — сборка **без** 1С.

## Предпочтительный адаптер r15

```text
explore(source, op, args)
  -> named dump path / alias (не «текущая единственная 1С»)
  -> once or daemon: bsl-indexer index --path <source>
       (инкремент по хешам; --force только явный полный пересбор)
  -> для C1/C2 метаданных и handlers:
       CODE_INDEX_HOME=<facade home>
       daemon.toml:
         [[paths]] path alias language="bsl"
         [tools] enabled = <explore subset>
         [cap] max_response_bytes = …
       bsl-indexer daemon run
       HTTP или stdio MCP: bsl-indexer serve --config <daemon.toml>
       (не добавлять --path: help v1.4.0 говорит, что --path игнорирует конфиг)
       tools/call с repo=<alias>
       subset: search_function / get_function / get_callers / read_file
               / get_object_profile / get_form_handlers
               / get_event_subscriptions / get_register_writers
               / find_references  (не все 33)
  -> без демона, только ядро:
       bsl-indexer search_function|get_function|get_callers --path <source>
       (1С-named tools недоступны)
  -> compact summary агенту; сырой tools/list не показывать
```

`[tools].enabled` уже в продукте: фасад не обязан патчить r15, чтобы
спрятать широкую поверхность (C10). Большой ответ режется `[cap]`.

## Две выгрузки

Несколько `--path alias=dir` или несколько `[[paths]]`; параметр `repo`
на каждый tool-call. Индекс не общий: `<root>/.code-index/index.db`.
Два корня обмена — два alias, не два глобальных «текущих проекта».
Одновременность двух живых `serve` NOT_RUN; контракт допускает один
процесс с несколькими открытыми БД.

## Оценка относительно цели

- Полезность: C1/C2/C11; C3 read метаданных и УФ; C9 через cap/фрагменты.
  Избегаем свой индекс/парсер BSL.
- Готовность: продуктовый бинарь; CLI ядра и MCP 1С-tools на sample готовы.
- Доказанность: static S1–S5; **CLI ядра RUN PASS**, **daemon+MCP
  RUN PASS** (`tools/list` = 33) и **whitelist RUN PASS** (`tools/list`
  = 9, отказ вне списка) на simple1CAiConf; точность графа на большой
  конфигурации не измерялась. stdio-whitelist не гоняли.

Рекомендация: **использовать как explore-core за фасадом**. Контрпример,
который её меняет: если без демона нельзя получить handlers/подписки, а
поднимать два процесса на каждый репозиторий запрещено средой — тогда
сузить explore до CLI ядра или пересмотреть обёртку, не состав.
