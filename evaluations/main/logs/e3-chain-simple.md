# E3 — сквозной прогон цепочки и цена контекста на стенде `simple` — 2026-09-22

Один проход по всей цепочке
`explore → docs → edit.view/apply dryRun → static → build → verify.unit →
verify.form → verify.scenario`, последовательностью отдельных вызовов
(не фасадом). Для каждой операции — реальный размер сырого JSON-ответа
(байты, строки), не оценка.

**Сумма «как есть» за один цикл** (все ответы целиком, включая docs и PNG):
≈ 289 857 байт. Без `docs` и PNG-файла (реалистичный сценарий, где оба
уходят в файл, а в чат — только summary): ≈ 31 655 байт — на порядок
меньше.

**Единственная операция, которая ОБЯЗАНА уйти в файл, а не в чат** —
`docs`: 77 205 байт / 800 строк (80 hits, 5 секций) — 26% от «сырого»
общего объёма цикла один этим шагом. Причина размера — Unica отдаёт
результат через асинхронную задачу (`unica.task.result` с опросом),
и финальный payload — полный список найденных мест, а не выжимка.
**Скриншот** (`verify.form`) — второй обязательный файловый артефакт:
180 КБ бинарных данных, JSON-обёртка отдаёт путь на диске, а не base64
(это уже сделано правильно продуктом, фасаду достаточно передать путь).
Все остальные шаги укладываются в единицы КБ и могут идти в чат целиком
или с лёгкой обрезкой.

## Список стыков между продуктами

1. **Формат 2.20 против 1.0.** `source-checkouts/simple1CAiConf` (`main`)
   — рукописный дамп формата 1.0. Unica читает его свободно (`view`,
   `docs`), но **отказывает** любой операции записи (`apply`, `check`):
   `"export format 1.0 is older than the writable profile 2.20 for 1C
   8.3.27; re-export the sources with the platform before editing them"`.
   Путь записи обязан идти через настоящий Designer-дамп 2.20
   (`.v8/work/simple-cf-220`). Фасад не может считать один и тот же
   `source-set` одновременно источником для explore/docs и целью для
   edit/static — если это разные дампы, это нужно явно развести.
2. **Кто держит ИБ.** Только r22 (`v8-runner`) создаёт и грузит файловую
   ИБ (`init`/`build`/`load`). Unica вообще не трогает ИБ напрямую — она
   читает/пишет только исходный XML-дамп на диске. Чтобы правка Unica
   попала в живую ИБ, нужен отдельный шаг `r22 build` поверх
   отредактированного дампа — это два разных продукта с разделённой
   ответственностью, не один сквозной вызов.
3. **Кто владеет рабочим дампом `.v8/work/simple-cf-220`.** Это
   производный снимок от r22 (`dump --mode full` из ИБ), не альтернативный
   «главный» источник. Он несёт следы предыдущих публикаций (smoke-
   `Comment` от `r01-publish-ifRev-20260921`) — повторный `dump` эту
   отметку затрёт молча. Фасад должен либо снимать такие рабочие дампы в
   новый каталог на каждый цикл, либо явно предупреждать о перезаписи.
   **Не тронуто в этом прогоне** — `apply`/`check` только читали `cf220`,
   Comment остался как был.
4. **`v8-runner` источник имени расширения — по source-set, не по
   реальному имени объекта.** `extensions`, `dump --extension`,
   `load --extension` резолвят цель по имени `source-set` в
   `v8project.yaml`, а не по фактическому `Name` расширения в самой ИБ
   (см. E1: несовпадение `yaxunit-shell` vs `YAXUNIT` давало
   `"не найдено"` при полностью активном расширении). Для
   extension-type `source-set` имя в yaml обязано совпадать с реальным
   именем объекта.
5. **Формат `--sources` YaXUnit не совместим с `format: DESIGNER`
   проектом** (см. E1): `tools download yaxunit --sources` даёт EDT-слой
   исходников, который не грузится в DESIGNER-проект; только
   скомпилированный `.cfe` через `load`/`merge` работает для нашего
   стенда.
6. **Асинхронный `docs`.** Ответ `unica.docs` — это тикет задачи
   (`status: queued/working`), а не результат; финальные данные приходят
   только через `unica.task.result` с опросом **в том же жизненном цикле
   демона/state-dir**, что и исходный вызов. Разные `UNICA_PROVIDER_
   STATE_DIR` для старта и опроса дают `task_transport_failed`. Фасад
   обязан удерживать один provider-state на всю пару «начать — опросить».
7. **Инкрементальная сборка r22 не всегда надёжна.** После насыщенной
   серии пересборок расширений (E1) обычная `build --source-set main`
   (partial-режим) отказала `"Ошибка чтения файла-списка загружаемых
   файлов"`; `--full-rebuild` прошёл чисто. Фасаду нужен fallback на
   полную пересборку, а не одна попытка incremental.

## Побочный пункт плана: smoke-`Comment` в `.v8/work/simple-cf-220`

Не тронуто в этом прогоне (только `apply dryRun`/`check`, оба read-only
относительно файлов дампа). Отметка `<Comment>r01-publish-ifRev-
20260921</Comment>` на `Documents/ЗаказПокупателя.xml` в `cf220`
по-прежнему присутствует и будет затёрта следующим `dump --mode full` из
ИБ без предупреждения, если не менять каталог назначения или не логировать
это явно перед прогоном.

## Вывод по `success_criteria[0]` (бюджет контекста)

Один полный цикл со всеми восемью операциями внешней поверхности
укладывается в единицы–десятки КБ на шаг, при условии что `docs`
(77 КБ) и бинарные артефакты (`screenshot`, 180 КБ) **обязательно**
уходят в файл, а в чат идёт summary + путь. При таком разведении
бюджет одного цикла для агента — **порядка 30 КБ текста в чате**, что
комфортно помещается в контекст. Без этого разведения (если бы фасад
наивно возвращал все сырые payload'ы) сумма превысила бы 280 КБ на один
цикл — это уже заметная доля бюджета за один шаг работы. Вывод:
бюджет контекста не является блокером **при условии**, что фасад
реализует пост-обрезку/выгрузку в файл для `docs` и любых бинарных
артефактов с самого начала, а не как доработку после факта.
