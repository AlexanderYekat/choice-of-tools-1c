Да. Для такой организации, как `1C-Migration-Lab`, где уже **37 репозиториев** и много пересекающихся MCP/skills/tools, лучшая практика — **не подключать всё к агенту одновременно**. ([GitHub][1])

Оптимальная схема, на мой взгляд:

> **маленькое постоянное ядро → маршрутизатор возможностей → ленивое подключение нужного набора инструментов → узкие результаты → выгрузка инструмента после этапа.**

Это важнее выбора конкретного MCP.

## Почему «подключим все MCP» — плохой вариант

Допустим, одновременно доступны:

* `code-index-mcp` — 32 инструмента;
* `ai-edt`;
* `mcp-bsl-platform-context`;
* `mcp-onec-test-runner`;
* Vanessa;
* `cc-1c-skills` / `cursor-1c-skills`;
* `onec-mcp`;
* `77MCP`;
* и ещё десяток специализированных вещей.

Один только `code-index-mcp` выставляет **32 MCP tools**. ([GitHub][2])

Проблема даже не только в токенах результатов. Модель должна постоянно видеть/различать:

```text
tool A
tool B
tool C
...
tool 97
```

и понимать:

> `find_references` или `code_search.references`?
> `mcp-bsl-platform-context.search` или `docs_lookup`?
> YaXUnit через `ai-edt` или через `mcp-onec-test-runner`?

Чем больше похожих возможностей, тем выше:

* tool-selection errors;
* лишние вызовы;
* повторный поиск тем же другим инструментом;
* context overhead от схем tools;
* вероятность, что агент выберет слишком тяжёлый инструмент.

В старом 1С-чате человек как раз жаловался, что **4–6 MCP заметно съедают контекст каждого запроса**.

# Интересно, что `ai-edt` уже пришёл ровно к этому выводу

Я сейчас посмотрел его актуальную архитектуру.

Раньше там было много отдельных tools. Теперь сделали **фасады**:

```text
code_search
diagnostics
edit_metadata
launch_debugger
insights
security_audit
docs_lookup
yaxunit_tests
...
```

Например один `code_search` скрывает за собой текстовый поиск, references, symbols, call hierarchy и т.д. ([GitHub][3])

Ещё важнее: у него появился режим **Canonical**.

Старые отдельные tools остаются вызываемыми, но **скрываются из `tools/list` именно ради уменьшения расхода контекста**. ([GitHub][3])

То есть авторы `ai-edt` фактически реализовали принцип:

```text
100 внутренних операций

        ↓

12 понятных фасадов

        ↓

LLM видит только 12
```

Вот это очень хорошая практика.

Codex

А:

                   AGENT
                     │
                     ▼

        ┌────────────┼────────────┐

     EXPLORE       EDIT         VERIFY

При этом агент **не видит всё содержимое этих веток сразу**.

# 1. Постоянно загружать только очень маленький router

Например в `AGENTS.md`:

```md
## 1C tools

For code/configuration exploration:
→ use skill: 1c-explore

For modification:
→ use skill: 1c-edit

For platform API questions:
→ use skill: 1c-platform-docs

For verification:
→ use skill: 1c-verify

For runtime debugging:
→ use skill: 1c-debug
```

Всё.

Не нужно помещать туда документацию 120 skills.

---

# 2. Skill должен быть маршрутизатором, а не учебником

Очень хороший принцип есть и в нынешних agent skill ecosystems: **progressive disclosure**.

В самом skill держишь только:

```text
когда использовать
        ↓
какой инструмент выбрать
        ↓
какой следующий reference открыть
```

Например:

```text
1c-explore/SKILL.md

Goal:
understand existing configuration without editing it.

Start:
1. code-index-mcp
2. If semantic EDT information required → ai-edt/code_search
3. If unusual bulk investigation required → RLM
4. Never load complete modules unless necessary
```

И уже только когда понадобится:

```text
references/
 ├─ code-index.md
 ├─ edt-semantic-search.md
 └─ rlm-investigation.md
```

Кстати, в вашем `cursor-1c-skills` уже появились буквально соответствующие правила:

* `skill-design.mdc` — **«лестница информации»**;
* `mcp-tool-priority.mdc` — маршрутизатор MCP под задачу;
* `file-edit-efficiency.mdc` — выбор инструмента по стоимости токенов;
* `agent-working-memory.mdc`;
* `agent-verification-patterns.mdc`. ([GitHub][4])

То есть направление там уже правильное.

---

# 3. `code-index-mcp` я бы сделал инструментом первого выбора для исследования

Именно потому, что он offline, детерминированный и дешёвый.

Сейчас его 1С-часть умеет, например:

* `get_object_profile`;
* `get_form_handlers`;
* `get_event_subscriptions`;
* `find_references`;
* `get_register_writers`;
* `find_path_bsl`;
* `get_role_rights`;
* граф связей данных. ([GitHub][2])

Поэтому вопрос:

> Где при проведении реализации пишется регистр Продажи?

не должен начинаться с:

```text
прочитай 250 файлов
```

А:

```text
get_register_writers("Продажи")
        ↓
find_path_bsl(...)
        ↓
get body только 2–3 нужных функций
```

Это чрезвычайно экономит контекст.

---

# 4. `ai-edt` — подключать, когда нужна семантика живого проекта

Например:

> Найди все реальные semantic references на реквизит.

или:

> Что EDT думает об этой ошибке?

или:

> Отладь серверный вызов.

Тут `code-index-mcp` уже не обязательно лучший источник, потому что EDT имеет собственную семантическую модель проекта.

То есть:

```text
обычный анализ
      ↓
code-index

неоднозначность / semantic truth
      ↓
ai-edt
```

А не оба постоянно долбят один и тот же вопрос.

У `ai-edt` даже есть подходящие профили:

* `Read-only`;
* `Editing`;
* `Debug & Test`;
* `Code Review`. ([GitHub][3])

Для агента это практически готовые **режимы работы**.

---

# 5. Документацию платформы вообще не надо держать постоянно

`mcp-bsl-platform-context` имеет всего пять довольно понятных операций:

```text
search
info
getMember
getMembers
getConstructors
```

и предназначен именно для поиска по Синтаксис-помощнику/объектной модели платформы. ([GitHub][5])

Значит, он должен появляться только когда агент реально задаёт вопрос вроде:

> Какие параметры принимает `ТаблицаЗначений.НайтиСтроки()`?

Во все остальные моменты он ничего полезного не даёт.

---

# 6. Проверку вообще лучше вынести в отдельную фазу

Вот это особенно важно.

Не надо, чтобы агент постоянно видел:

```text
run_all_tests
run_module_tests
build_project
dump_config
launch_app
check_syntax_edt
check_syntax_designer...
```

Хотя `mcp-onec-test-runner` действительно всё это предоставляет. ([GitHub][6])

Лучше:

```text
IMPLEMENT phase
    ↓
только edit tools

код готов
    ↓
переход VERIFY
    ↓
подключается verification pack
```

Например:

```text
verification-pack

1. static check
2. build
3. targeted YaXUnit
4. smoke test UI
5. full Vanessa regression only if required
```

---

# 7. И результат tool-а тоже нельзя просто вываливать в контекст

Это вторая половина проблемы.

Даже один хороший MCP может загадить контекст вот так:

```text
find references

→ 972 результатов

→ все 972 отданы LLM
```

Плохо.

Лучше:

```text
find references
        ↓
count = 972

groups:
 CommonModule = 610
 Documents = 155
 Forms = 134
 Reports = 73

top suspicious = 12
```

Затем агент:

```text
show group Documents
```

и получает 20.

Потом:

```text
show Document.Реализация
```

и получает 4.

То есть **progressive narrowing**:

```text
10000
 ↓
500
 ↓
50
 ↓
5
 ↓
код
```

А не:

```text
10000 → prompt
```

---

# 8. Ещё лучше — разделять поиск и чтение

Я бы жёстко ввёл правило:

> Search tools никогда не должны по умолчанию возвращать полный исходный код.

Например:

```json
{
  "symbol": "ОбработкаПроведения",
  "module": "Документ.Реализация.МодульОбъекта",
  "lines": [435, 612],
  "relevance": 0.94
}
```

А уже отдельный:

```text
read_symbol(...)
```

возвращает код.

Это то же самое, как хороший IDE:

```text
symbol list → navigate → open
```

а не:

```text
search → открыть одновременно 400 файлов
```

# 9. Отдельные агенты тоже могут помогать с контекстом

Например основной агент не обязан видеть всё исследование конфигурации.

Можно:

```text
MAIN AGENT
   │
   ├── explore-agent
   │       ↓
   │   code-index / RLM
   │
   ├── edit-agent
   │       ↓
   │     ai-edt
   │
   └── test-agent
           ↓
      YaXUnit / Vanessa
```

А обратно передавать не весь лог:

```text
explore-agent:
«Я прочитал 87 файлов...»
```

а структурированный handoff:

```yaml
finding:
  affected_objects:
    - Документ.Реализация
    - РегистрНакопления.Продажи

call_path:
  - ОбработкаПроведения
  - СформироватьДвижения
  - ЗаписатьПродажи

relevant_code:
  - module: ...
    lines: 438-492

confidence: high
evidence: ...
```

Это **огромная** экономия контекста.

## Что бы я сделал у тебя конкретно

Для твоего рабочего Codex/Cursor я бы не ставил все 37 репозиториев как MCP.

Я бы сделал всего **5 видимых возможностей**:

```text
1c_explore
1c_docs
1c_edit
1c_verify
1c_debug
```

А внутри них router решает:

```text
1c_explore
   ├─ code-index
   ├─ ai-edt
   └─ RLM

1c_verify
   ├─ BSL LS
   ├─ YaXUnit
   ├─ Answer42
   └─ Vanessa
```

Фактически это тот же принцип, к которому уже пришёл `ai-edt`: **много внутренних операций, мало фасадов, видимых модели**. И я бы распространил его уже на **всю экосистему 1C-Migration-Lab**. ([GitHub][3])

### А самый важный принцип

Не считать context window хранилищем знаний.

```text
Knowledge lives:
  index
  database
  files
  docs
  artifacts
  tools

Context contains:
  current goal
  current plan
  current findings
  minimal evidence
  next action
```

Вот тогда даже 100 инструментов не проблема — **если модель одновременно видит только 5–10 релевантных**.

И, кстати, это очень хорошо ложится и на твой `Intelligence-researcher`: я бы там заложил **capability registry + dynamic tool profiles** на уровне оркестратора, а не давал каждому worker весь набор MCP.
